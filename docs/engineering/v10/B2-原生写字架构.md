## 0. 结论

**选方案 A′：一个运行时、一份 store，原生页面只是视图。** 规则与 store 继续只在 WKWebView 里运行（`store.commit` 仍是唯一写入口，B1 的原生 SQLite 仍只由它写）；原生写字页经一组「写字会话 API」读快照、提交操作。为了让「写字中途不等桥」，读取改成**页面推快照**（open 消息带快照，每次提交的回包带下一份快照），书写本身（落笔、画、抬笔、撤销、清空）完全在原生内存里，抬笔后把笔画「发出去不等」；只有判断这类 D07 写入点才等回包。原生页**盖在** WKWebView 上（全屏覆盖呈现），不进导航栈把网页移出窗口——实测网页一旦离开窗口，WebKit 降速，判断往返从 p50 ≈ 20ms 变成 50–100ms。D26 原计划的 JavaScriptCore 不在 B2 引入：它带来的只有第二份内存状态；JSC 留到 B3「网页页面全部退场」那一刻作为同一套 JS 的新宿主（仍是一份），B4 再换成 Swift。

## 2. 方案比较

| | A′ 原生视图 + WKWebView 运行时（选定） | B JSC 里再跑一份规则与 store，与 WKWebView 共享 SQLite | C 状态移到原生（Swift store），JS 规则在 JSC 里当纯函数 |
|---|---|---|---|
| 一致性 | 一份内存状态、一个写入者。原生页面没有自己的业务状态，只有「这一字正在写的笔画」 | **两份内存状态**。JSC 提交后 WKWebView 的镜像过时：要么每次提交后让 WKWebView 重读 SQLite 并整体替换（store 的 `isReplacement` 会让网页每页按新状态重来、写字页现场丢弃），要么在两边做增量同步协议；谁是权威只能靠「同一时刻只有一边写」的约定，B2 期间结果页（网页）改判、字详情改判与原生写字页并存，约定守不住 | 一份状态（Swift），但 store / storage / budget / schema / 迁移约 2,800 行要先改 Swift，网页页面也要改成经桥读写——等于把 B4 的一半提前，且两种语言的 store 同时存在 |
| 写字中延迟 | 书写全在原生；抬笔「发出去不等」；判断 1 次往返（模拟器 p50 ≈ 20ms，见 §7） | 书写同 A′；判断在进程内 JSC，约 5–10ms（同步 SQLite 仍在） | 同 B |
| 失败语义（D07） | 不变：判断回 `{ok:false}` 原生留在判断页三段式；回包带快照，结果未知后重发靠「已不是当前字」对账（§3.3） | 要重做 JSC 侧的同步落库与回滚，且要保证 WKWebView 那份不会在失败后被「刷新」成半态 | 要在 Swift 里重做全部三段式与回收重试 |
| 新增工程 | 会话 API（一个 JS 模块）、原生页面、宿主条目（路由一个开关） | JSC 宿主：ES 模块在 JSC 里没有加载器，需要打包步骤（新增构建工具）；`ui/screens/write/*.js` 的提交函数依赖 Preact，要先拆出来；`fetch`/XHR/`performance`/定时器垫片 | 同 B + Swift store |
| B3 演进 | 页面逐个换原生，API 照用；当最后一个网页页面退场，把同一个无 DOM 的「会话 + store」模块搬进 JSC（届时没有第二份）。在那之前任何时刻都只有 WKWebView 一个运行时 | B3 时仍要解决两份状态 | 已在终点附近 |
| B4 移除 JS | 会话 API 就是 B4 的移植边界：Swift 实现同一组 op，`test/ui/native-write.test.mjs` 与 XCTest 换实现照跑 | 同左，但先要拆掉 B 的同步机制 | 只剩规则函数要移植 |

**否掉 B**：两份内存状态互相覆盖是这个项目最不能接受的风险（D07 / D27 的笔迹留存、结果页改判、跨天作废都建立在「store 就是真相」上），而它换来的只是判断提交快 10ms 左右——A′ 的判断往返已在一帧到两帧之间，而且发生在点「写对了」之后、有 320–440ms 的判断键就绪编排与换字淡化遮着。**否掉 C**：违反 D67「规则不重写、test/ 为契约」，把 B4 的工作量与风险提前到 B2。**D26「规则由 JavaScriptCore 承载」的调整**：JSC 只在它能成为**唯一**运行时的时候引入（B3 末，见 §8 B3 衔接），B2 期间由 WKWebView 承载同一套 JS——目的（现有 JS 当规则合同、原生写页面）不变，载体推迟。这条需要主控 / 负责人确认后记进决定表。

## 3. 写字会话 API

页面侧 `src/ui/screens/write/native-session.js`：`window.shiziNativeWrite(op, args) → Promise<{ok, …, ms}>`（B2.1 起 API 本体在无 DOM 的 `src/session/write-api.js`，页面侧只注入导航与颜色，见 §12）。原生侧 `NativeWriteBridge`（`callAsyncJavaScript`，参数按值传，不拼脚本）。每个 op 调用网页写字页**同一个**提交函数，所以规则、记录形状、FSRS、笔迹编码与网页逐字段一致（`test/ui/native-write.test.mjs` 用同一组输入分别走网页路径与 API 路径，断言整份 store 状态 `deepEqual`）。

### 3.1 已实现（B2.0）

| op | 参数 | 调用的现有函数 | 写入语义 | 回包 |
|---|---|---|---|---|
| `open` | `{slot}` | `persist.commitRecover`（恢复幂等，01 §3.3） | 需要时一次 commit | `snapshot` + `copy` + `colors` |
| `strokes` | `{slot, cardKey, strokes, phase}` | `persist.commitStrokes` | P52 不阻断：原生不等 | `{ok}` |
| `phase` | `{slot, cardKey, phase:'compare'|'recall', strokes?}` | `compare.commitComparePhase` | P52 不阻断 | `{ok}` |
| `judge` | `{slot, cardKey, judgment, strokes, hints}` | `compare.commitJudgment`（记录 + FSRS + 会话推进 + 笔迹 + D27 回收，一个事务）；这组写完时同一次调用里 `result.commitFinish` | **D07：原生等回包，成功才推进** | 成功：`recordId`、`finished?`、下一份 `snapshot`；失败：`error.kind` + 当前 `snapshot` |
| `exit` | `{slot, to:'back'|'result', sessionId?}` | `nav.back()` / `result.openResult` | 只导航 | `{ok}` |
| `copy` | `{keys}` | `copy/index.t` | — | 文案字典 |
| `hint`（B2.2） | `{slot, cardKey, action: state / give / range, totalStrokes, used, range, written, hints, hintRange}` | `ops/hint` 的 `hintStep` + `commitHintStep`（整字给完 = `commitAnswerSeen` stay）/ `commitHint('hint-fade')` | P52 不阻断（写入失败照给，原生照常显示） | 按钮模型、说明、`given` / `hintRange` / `used` / `whole` / `announce` |

快照（`writeSnapshot`，纯函数）：`{slot, active, sessionId, kind, cursor, total, done, cardKey, char, phase, storedPhase, strokes, hints, prompt:{cells, hint}, lastLine}`。笔画在桥上是紧凑数组 `[[x, y, t, p?]…]`（345 单位，t 为毫秒，p 只在 Pencil）。回忆阶段答案字只在 `char` 字段（画参考格用），不进任何读屏名称（D16）。

**B2.1 先做的一步**：把这些提交函数（现在散在 `src/ui/screens/write/*.js`，与 Preact 组件同文件）原样挪到无 DOM 的 `src/session/`（`write-ops.js`），网页写字页与会话 API 都从那里导入。行为不变（现有单测全部照跑），但会话 API 从此不依赖任何 UI 模块——这是 B3 搬进 JSC、B4 移植 Swift 的边界。

### 3.3 顺序、幂等与对账

- `callAsyncJavaScript` 在页面主线程按发出顺序执行，所以先发的 `strokes` / `phase` 一定先于随后的 `judge` 落库。
- 所有写入 op 都以「`cardKey` 仍是当前字」为前提（与网页写字页同一检查），否则回 `stale`。`judge` 失败回包也带快照：桥超时或页面重载导致「结果未知」后重发时，若上一次其实已提交，页面回 `stale` 且快照已是下一个字，原生按成功对账，不会多记一次（D07「重试不重复计数」）。
- 页面重载（WebContent 进程被回收）：原生页留在屏上，本地笔画留在内存；路由恢复出写字条目后宿主再发 `open`，原生用新快照重新同步（同一个字时保留本地笔画）。

## 4. 导航、转场与恢复

- **网页路由仍是真相源**（B2 期间）。所有写字入口照旧调用 `session/index.js openWrite(slot)`，写字条目照常 `push` 进网页路由并写进路由提示 `shizi.v2.route`（冷启动恢复、刷新、提醒深链压过恢复，全部沿用 01 §7）。
- **原生宿主条目**：开关打开时 `write` 屏渲染成 `NativeWriteHost`（`registerScreen` 新选项 `nativeHost`）：不画内容、本层透明、不接收触摸，`root.js` 让下层页保持可见（原生页滑走时露出的就是下层的首页 / 字库 / 结果页）。宿主挂载时 `postMessage({type:'nativeWrite', op:'open', slot, animate, via, payload})`，`payload` 就是 `open` 的回包——原生首帧不等桥；卸载时 `op:'close'`（深链换组、跨天作废、阻断页、store 整体替换都会卸掉宿主，原生页跟着离开，不发 exit）。
- **呈现方式**：原生写字页以 `.overFullScreen` + 自定义转场盖在 `WebViewController` 上，**不用 `UINavigationController` push**。原因（B2.0 实测）：push 完成后底下的 WKWebView 被移出窗口，WebKit 对不可见网页降速，`judge` 往返从 p50 ≈ 20ms（p95 ≈ 28ms）变成 50–100ms（页面内执行只有 8ms）。覆盖呈现时网页一直在窗口里、只是被盖住，不降速。
- **转场**（`NativeWriteTransitions`，一个对象）：B2.0 只有推入（自右滑入 350ms）/ 滑出、左缘交互式滑回（`UIPercentDrivenInteractiveTransition`，阈值与网页同一函数 `BackGestureThreshold.commits`，P103）、写完最后一字淡出到结果页（150ms，D20 无中间页）、减少动态效果 150ms 淡化。B2.8 在同一对象里加 D62：`via:'home'` 时纸从被点按钮展开 / 缩回（T-paper，来源矩形由宿主随 open 带来）、其他入口 T-push、通知 / 冷启动恢复 T-quiet；同时让网页侧对宿主条目不再播自己的纸展开（现在两边都播，网页那份在透明层上看不见但白跑一遍）。
- **返回**：左上「‹」、左缘右滑、读屏两指 Z 形是同一个动作（N3）：回忆阶段 = 离开（转场完成后发 `exit {to:'back'}`，页面 `nav.back()`；现场在抬笔时已写回，P52）；判断阶段 = 「接着写」（`phase recall`，墨不变）。
- **冷启动恢复**：杀进程重开 → 页面按路由提示恢复出写字条目 → 宿主 `open {animate:false}` → 原生直接盖上，回到正确的字、正确的阶段与笔画（模拟器实测：写到第 2 字一半杀进程，重开回到第 2 字、两笔都在）。
- **B3**：首页、字库等改原生后，导航真相源移到原生（`UINavigationController`），写字页成为普通原生子页；会话 API 不变。

## 5. 文案、颜色与字形：单一来源

- **文案**：原生页面不写任何用户可见的字。`open` 回包带 `copy` 字典（键表 `NATIVE_WRITE_COPY_KEYS`，值由 `src/config/copy` 的 `t()` 给出，带 `{n}` 占位的由原生替换）。门禁 `test/ios-native-write.test.mjs`：原生写字页 Swift 源码里不得有含汉字的字符串字面量；原生用到的每个键都在键表里。B4 去掉 JS 时改为构建期从 `src/config/copy`（已有 `copy-source.json` 逐字核对）生成 `Copy.json` 进包，Swift 读同一份。
- **颜色**：`open` 回包带页面此刻的令牌计算值（`--paper --hand --ref --frame --ink1–4 …`，浅深色自动跟随）。B3 起改为 `tokens.json` 生成颜色集（沿用 `generate-paper-colorset.mjs` 的做法），网页与原生同源。
- **练习字字形**：原生直接读包里的 `Web/data/<字>.json`（与网页同一批文件，01 §8.7），SVG 路径解析成 `CGPath`，仿射与 `glyph.js glyphTransform` 相同；没有数据时退回整字（10.13 语义）。

## 6. 书写面：从 spike 转正（B2.1）

`NativeInkView` 已在纵切里作为原生写字页的书写格使用（同一个类，DEBUG）。转正清单：

1. 移出 `#if DEBUG`，与 `InkModel` 一起进 Release；`verify-archive.sh` 删掉对应的「Release 不含」断言，改为断言 spike 叠层（`NativeInkSpike`）仍不进 Release。
2. **Apple Pencil（D32）**：压力、倾角已进原始点；补悬停（`UIHoverGestureRecognizer` + `zOffset`，悬停时画落点预览，不落墨）、双击（`UIPencilInteraction`，按系统偏好映射到「撤销」或「清空」，读 `preferredTapAction`）、Pencil 时手指不落墨（`allowedTouchTypes` 按「上一次输入是 Pencil」切换）、掌托（接触面积 / 静止判定，规格 §2.1 / T10）。
3. 抬笔 70ms 补间（规格 §7.4）、前缀冻结增量（§7.2，真机 `frameCpuMs.p95 > 4ms` 时）、飞白 / 洇墨 / 纸纹 / 湿墨变干（§5）、发丝线（§6.3）。
4. **一个渲染器**（规格 §6.1）：判断页上格、结果页作品、字墙、详情等原生页面全部用 `InkModel` 渲染原始点；网页剩余页面在 B3 前继续画旧墨（已知差异，见 §10 风险 3）。
5. 换字后 250ms 落笔持住（P227）、0.4s 防误点、转场中落笔「动画一帧到终态、这次输入照常生效」（T0 规则 3）——纵切里没做，实测会丢掉判断回包前落下的那一笔。
6. 读屏：`allowsDirectInteraction` + 每笔播报「n 笔」（A2-06，文案键 `X-WRITE.gridLabelCount` 已在用）。
7. 金标准自检（`InkModelCheck`）挂进 XCTest（现在只在 `-shizi-ink-selfcheck` 启动参数下跑）。

## 6.1 笔迹由谁写入

**B2：仍由判断事务写**（页面 `commitJudgment` 里 `setInk`，与记录、FSRS、会话推进同一个原生事务）。原生不直接写 SQLite：两个写入者会破坏「一次判断 = 一个事务」（D07 原子性）与 store 内存镜像的一致。原生只把原始点交给页面（已是 `encodeRawStrokes` 同一格式）。
**B2.3 升级**（B1 报告建议）：`ink` 表 schema 2 改为每条记录一行、存原始点（`encodeRawStrokes`，D27 留存规则不变），页面的 `setInk` 写这一行；这样原生渲染器回放的是真实笔迹（规格 §6.4「Ink v3 只能近似回放」的问题消失），存储也不再按月整块重写。写入者仍只有 store。

## 7. 纵切实测（iPhone 17 模拟器，iOS 26.5，Debug，60Hz；不代表真机）

| 量 | 结果 | 说明 |
|---|---|---|
| 落笔 → 帧预计上屏（`targetTimestamp`） | p50 8.5ms、p95 16.0ms（n = 50 个合并点） | 与 spike 同一钩子（spike：8.95 / 15.8）；模拟器注入触点本身有 ≈ 9.6ms 投递延迟；`presentedTime` 模拟器没有 |
| 每帧 CPU（分析 + 几何 + 编码） | p50 2.0ms、p95 5.5ms（Debug，-Onone） | 60Hz 预算内；真机 120Hz 下 p95 > 4ms 时做前缀冻结（§6 第 3 条） |

## 10. 风险

1. **WebKit 降速**：网页一旦离开窗口（或 App 进后台）桥变慢。对策：覆盖呈现（已做）；B3 网页页面逐步退场时，必须保证 WKWebView 仍在窗口里（隐藏在原生页面下面），直到最后一个网页页面退场、运行时换成 JSC。真机要复测 120Hz 下判断往返。
2. **转场叠播**：网页对宿主条目仍播自己的纸展开 / 推入（透明层上看不见），在低端机上多一份主线程工作；B2.8 关掉。
3. **两种墨**：原生书写格用 ink-model-1.0，判断事务存的 Ink v3 是旧管线烘焙的宽度，结果页（网页）画旧墨——同一个字在写字页与结果页粗细不同。B2.3 存原始点、B2.6 结果页原生后消失。
4. **换字时窗**：判断回包前落下的笔会被新字快照清掉（纵切实测可复现）——B2.1 已在书写面修（持住到下一个字、换字后 250ms 门限、书写面移动时按屏幕位置换算，§12）；B2.2 正式版式里复核。
5. ~~**会话 API 依赖 UI 模块**~~：B2.1 已拆到 `src/session/`（§12），门禁 `test/session/boundary.test.mjs` 守住。
6. **D26 措辞**：B2 不引入 JSC 与 D26 / D67 的字面描述不同，需要决定表记一条（目的不变：现有 JS 是规则合同）。
7. **模拟器数字**：全部是 Debug 模拟器 60Hz；真机 T1（落笔到上屏 ≤ 备忘录 + 1 帧）仍要 240fps 录像。

## 13. B2.3 实施记录（笔迹存原始点 · ink schema 2）

**落盘形态**：内存里 `state.ink[月][id]` 不变（getInk / setInk / deleteInk、D27 回收、预算回收、备份都照旧按月分组）；**落盘每条墨迹一个键** `shizi.v2.ink.<YYYY-MM>.<recordId>`（`schema.inkRecordKey`，spec id `inkRecord`，只是存储层的键、不进备份）。原生 SQLite：`user_version` 1 → 2，新表 `ink_records(month, id, body, PRIMARY KEY(month, id))`，一键一行；旧 `ink(month)` 表只剩没迁完的旧月行。localStorage 同一套键。setInk 只让这一条变脏 → 判断提交只写这一行（不再重写整月）。

**判断墨迹的编码（Ink v4 原始点）**：`{v:4, c:345, r:['<base64>'…], g:[ms…]}`。r 每笔一个打包串，与 `encodeRawStrokes` 那一行逐整数互逆（0.1 单位 / 1ms / p 0.001，不抽点、不烘焙宽度）：首字节 stride，之后每点 zigzag(Δx)、zigzag(Δy)、dt、(zigzag(Δp)) 的 LEB128；g = 笔间停顿。**没有直接存 JSON 整数行**：实测每点约 13 个字符，120Hz 常用 300 字 × 2 份 4.82MiB；打包后 1.77MiB（约 37%）。
- 读：网页 `decodeInk(v4)` = 解出原始点 → `buildStroke(final)`（书写时同一管线，按墨迹对象缓存）；原生 `InkStoredInk.decode`（InkModel.swift，Release）→ 原始点 → `NativeInkStrokeMesh.build` / InkModel（规格 §6.4「与书写时逐样本一致」）。v3 / v2 旧数据照常读。
- **编码按后端选（policy P05，与卡面不一致处）**：原生 `nativeStorage.inkFormat = 'raw'`；网页 localStorage `inkFormat = 'v3'`。原因：原始点约为 v3 的 2.86 倍（120Hz 常用 300 字 × 2 份 1.77 vs 0.62MiB），localStorage 5MiB 装不下 D27 永不回收的「每字第一次 + 最近一次」。store 经 commit 的 `ctx.inkFormat` 交给写墨的 mutate（judge / 看后自写），网页路径与 API 路径同一个 store 所以仍逐字段相同；store 契约（键、迁移、只写一行、D27）两种后端完全一致。
- 实测容量（UTF-16 估算口径，test/core/ink-math.test.mjs）：v4 每份 60Hz 1.9KiB、120Hz 3.0KiB、Pencil 240Hz 5.7KiB（12 画以上 2.7 / 4.4 / 8.1KiB）；原生墨迹预算 32MiB ≈ 120Hz 5400 字 × 2 份、240Hz 重字约 2000 字 × 2 份。

**迁移**（schema 1 → 2，两段，都可重入、失败不丢数据）：

## 19. R10-A 实施记录（D71 ②「笔画写完消失」+ D71 ① 墨粗回退）

**根因（笔画消失）**：写字页左缘返回用 `UIScreenEdgePanGestureRecognizer`（`edges = .left`，挂在整页上，默认 cancelsTouchesInView）。它的起手区不是 20pt：UIKit 的 `_UISEGestureFeatureSettings._edgeRegionSize = 40.2pt`（iOS 26.5 实读），还按手指接触半径（`_touchRadiusScaleFactor`）放宽、按速度往回推算起手点（`_backProjectTime`）。书写格从 x = 20（书写面 21）起，于是格内左侧约 20pt 落在系统起手区里：手指在那里起笔向右写（横、提），识别器开始 → `handleEdgeBack(.began)` 丢掉这一笔、UIKit 再发 touchesCancelled → 交互式返回位移不够、回弹 → 页面不动，刚写的笔不见了。只在「格内左侧 + 向右为主 + 手指（接触半径大）/ 快写」时发生，所以「写在某些部位会、有时又不会」。网页版的起手带只占页边 12px、不压书写格（src/ui/edge-swipe.js），没有这个问题。
**复现**：iPhone 17 模拟器 XCUITest 合成触摸（接触半径近 0，比真手指难触发）：在格内 x = 5 / 15 起笔向右的 4 笔里 2 笔被 touchesCancelled 丢掉（首轮）；之后数轮 ~100 笔未再出现——模拟器上偶发，真机手指（半径 10–20pt）更易触发。DEBUG 笔画日志（`NativeInkView.strokeLog`，探针 `native.inkLog`、控制台 `[shizi] ink …`）记每一笔的结局：began / ended / held / cancel:<reason>（edge-back / touches-cancelled by [识别器@视图] / palm / reset）/ refused:<原因> / pending-dropped / pending-cleared。
**其余可疑点核实**：drawable 只在判断阶段（非提交中）为 false，回忆 / 描一遍 / 凭记忆写恒为 true，书写中途不变；首练说明收起、结果行收起引起的版式变化走 `remapStrokeInProgress`（笔不断）；换字门限内的笔持住到点交出（P227），只有判断 / 跳过写失败时 `dropHeld`（设计如此）；快照回包（resync / 改判）同一字一律 keepLocal；改判结果行热区、撤销 / 清空、求助行没有压到书写格（格下沿 2–30pt 起笔逐一实测保留）。以上都不是原因。
**修法（规则，不是补丁）**：书写格里起手的触摸一律归书写，左缘返回只在格外（页边）生效——`edgeBack.delegate = self`，`gestureRecognizer(_:shouldReceive:)` 在书写面可写（drawable、未隐藏）且按下点在书写面内时拒收（`NativeWriteViewController.edgeBackReceives`）。判断页上格不可写，左缘照常（接着写）。被系统中断的笔仍按规格丢弃（与网页 pointercancel 同语义：ink-canvas.js「中断一律丢弃未完成的当前笔」），不改成按抬笔保留。

## 21. R11-B 实施记录（D72 ③ 格外起笔、滑进书写格）

**规则**：页面空白处起手（不在按钮 / 可点控件上、不在左缘返回起手区）的单指或 Pencil 触摸，滑进可写的书写格时在进入点开始这一笔（进入点 = 轨迹与格边的交点，时间按前后两采样插值），之后照常写；格外那段不画、不存。起手在按钮上仍是按钮（滑走 = 取消），起手在左缘返回区仍归返回（R10-A 不变）。判断页等不可写阶段、格被弹层盖住时不生效。写进交互规范 G1 / G3。
**做法**：写字页根视图改成 `NativeWritePageView`（NativeWriteViewController.swift），只覆写 touches*，不加识别器、不放大书写面命中区：UIKit 把起手在按钮上的触摸交给按钮，到不了根视图；起手在空白处（命中根视图，或命中题面 / 说明 / 底栏这些不接触摸的底板、经响应链转上来）的才到这里。`approachStarts` 再排除：起手点在 `edgeBackZone`（40.2pt，系统左缘识别器起手区实读值）以内、在书写面里（格内起手归书写面自己的 touchesBegan，不变）、命中视图链上有 UIControl。符合的交给书写面「待进入」（NativeInkView 触摸输入段 `approach*`）：只记上一采样；第一次进格（`entryPoint`，Liang–Barsky 取最后进入的那条边，坐标贴到边上，时间 / 接触半径 / 压力 / 倾角同比插值）时，要求进格处 `hitTest` 落到书写面（可写、没被弹层盖住），然后以进入点走同一个 `inputBegan`——一次一笔、Pencil 优先、手掌（D72 ①，只在用过 Pencil 后）、换字 250ms 持住都照旧——余下采样走 `inputMoved`，抬笔 / 取消走 `inputEnded` / `cancelStroke`（左缘返回识别成功时 UIKit 发 touchesCancelled，这一笔按中断丢弃）。根视图 `isMultipleTouchEnabled = true`，掌托与 Pencil 同时在格外落下时每个触点都收得到。DEBUG 笔画日志多两种：`enter x= y=`（进入点，书写面坐标）、`approach-blocked`（进格处不是可写的书写面）。
**现状核实（起手在格内、写出格外，不变）**：触摸始终归书写面，这一笔不断；格外的点照常记进原始点（345 单位可 < 0 或 > 345），画面只显示格内（CAMetalLayer 就是书写面大小）；滑回格内接着画，抬笔才结束。与网页 setPointerCapture 同语义。
**检查**：ShiziWriteTests `EnterFromOutsideTests`（四条边与角上的进入点、时间与 Pencil 字段插值、只认「外 → 内」；书写面上走一遍：从边开始、格外段不进原始点、最后一段才进格也算、弹层盖住 / 不可写不开始、一次一笔 / Pencil 抢先 / Pencil 刚用过手指不落墨、手掌、换字持住；写字页哪些起手可以当格外起笔）；ShiziUITests `test206`（格上方 / 右侧 / 下方空白起手滑进：笔数 +1、日志 ended、enter 点在对应格边）、`test207`（撤销按钮上起手滑进格：不出墨、不撤销）、`test208`（屏幕左缘起手滑进格：离开写字页、会话 0 笔）。
