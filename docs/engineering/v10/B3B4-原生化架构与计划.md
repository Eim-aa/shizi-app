## 0. 结论（一页）

1. **B3 继续 A′「一个运行时、一份 store」**：B3 全程规则与 store 只在 WKWebView 里跑（D69 不变的部分），原生页面全部是视图，经一个扩展后的「App API」（`window.shiziNative`，沿用 B2 写字会话 API 的契约：网页路径 == API 路径）读写。
2. **UI 用 UIKit，不用 SwiftUI**（推翻路线文档「改 SwiftUI」的写法）。理由见 §3.1：现有约 9,600 行原生界面全是 UIKit（`import SwiftUI` 0 处），自定义转场 T-paper / T-quiet / 跟手返回、逐屏对比按 UIKit 视图树取元素、最低系统 iOS 15。
3. **导航分两段**：段 1（B3 各页面卡）**网页路由仍是真相源**，原生页面一律是 `registerScreen` 的原生宿主条目，原生侧一个通用的 `NativeStage`（由 B2 的写字 / 结果协调者推广而来）把「网页栈顶上连续的原生宿主」画成一个原生导航栈；冷启动恢复、深链、阻断页的语义一行不动。段 2（**B3.F，全部页面原生后**）把真相源翻到原生 `UINavigationController(root: UITabBarController)`，路由提示仍由 JS 单一写入者写、恢复判定仍由 JS 给出。
4. **JavaScriptCore：推荐不引入（修订 D69 后半句）**。负责人只在全部原生（B4 完）后统一测试，「B3 末换 JSC」这个中间态没有人会用到；它要新建打包工具链（仓库没有任何打包器）、垫片与第二套桥，B4 又整个拆掉。B3 末起 WKWebView 作为**无界面引擎**留在窗口里（全尺寸、压在原生层下面、不隐藏，避开 WebKit 降速），直到 B4 换写入者。若主控坚持 D69 原文，§4.4 给了具体做法与时点（B3.F 之后、B4.5 之前，卡 B3.J）。
5. **B4 的移植边界 = App API 的 op 表**：B3 起原生页面只依赖 Swift 协议 `ShiziEngine`（B3 实现 = `WebEngine` 经桥调 JS），B4 写一个 `SwiftEngine` 实现同一组 op。规则与数据写成一个只依赖 Foundation 的 Swift 包 `ShiziCore`，能编进 App，也能编成 macOS 命令行，供 node 侧**同一操作序列 JS vs Swift 逐字段差分**、调度模拟器 20 场景 27 条不变量双引擎跑。
6. **一次性切换写入者**（B4.8），切换前 DEBUG 影子运行（每次 JS 提交同时让 Swift 算一遍、比对整份状态）；SQLite 表结构与值的 JSON 形状不变，切回 `WebEngine` 即回退。
7. **门禁**：网页参考图在**第一张页面卡开工前一次取齐**（B3.3，网页那时还在维护）；QA-H1 的状态改为数据驱动（夹具 + 路由），每页卡只加夹具文件、不改共享枚举；网页退场后 130 个 Playwright spec 按 §5.3 映射到 node 规则测试（B4 后是 ShiziCore 测试）与 XCUITest。
8. 分卡：B3 共 19 张（含本卡）、B4 共 11 张，分 8 个波次（W0–W7）；见 §6。

### 3.3 导航

#### 段 1（B3.2 – B3.13）：网页路由仍是真相源

- **每个原生页 = 一个原生宿主条目**：`registerScreen(name, comp, { nativeHost })` 已有（router.js:43；write 与 result 在用）。B3.2 把它推广为通用开关：`native: true` 的屏在开关打开时渲染成透明宿主（`root.js` 已支持透明 + 下层可见），挂载发 `{type:'native', op:'open', screen, params, via, rect?, payload}`，卸载发 `close`。
- **原生侧 `NativeStage`**（取代 `NativeWriteCoordinator` 里写字 / 结果专用的那套）：维护一个原生导航栈 = 网页栈从顶往下**连续的原生宿主条目**；栈顶是网页页面时整个原生层让开（B2.7 结果页「为字详情让开」的做法），网页自己画转场。原生层根视图盖在 WKWebView 上，**WKWebView 一直在窗口里**（B2 §10 风险 1）。
- **屏名 → 视图控制器**：不设共享登记表。按命名约定 `@objc(ShiziScreen_library_all)` 由 `NSClassFromString` 找类（屏名里的 `-` 换 `_`），找不到 = 该屏还没原生，宿主不启用（JS 的 `native` 开关只在 `open` 回 `{ok:false, reason:'no-native'}` 时降回网页）。所以每张页面卡只新增自己的 Swift 文件与自己 JS 屏文件里的一个选项，**不改任何共享文件**。一个 node 测试核对「标了 native 的屏 ⇔ Swift 里有同名类」。
- **原生页里发起的导航**：原生点按 → `nav.push / nav.replace / nav.back / nav.tab` op → 网页路由执行（所有入口规则——D62 来源矩形、D70 例外、S4 撤销交接——都还是 JS 那一份）→ 宿主挂载回发 `open`（带下一页的视图模型）→ `NativeStage` 播转场。量测门槛：点按到转场第一帧 p95 ≤ 50ms（模拟器 Debug；B2 判断往返 p50 ≈ 20ms）。
- **转场**：`ShiziTransitions` 一个对象（B2 `NativeWriteTransitions` 推广）——T-push（300ms、下层视差 −30%、左投影）、T-paper（来源矩形由 `open.rect` 带来）、T-quiet、减少动态效果 150ms 淡化；全部时长 / 曲线取生成的 motion 令牌。**原生 ↔ 网页**之间的转场（段 1 期间才有）一律由「上面那一层」播：网页推入网页页面盖住原生页时，原生层先截图留底再让开（`NativeResultCover` 的做法）。
- **返回**：左缘识别器、左上「‹ / ×」、两指 Z 形是同一个动作（N3）。原生页登记返回种类（`page` / `phase`），跟手画面在原生播完后发 `nav.back {via:'native'}`，网页路由出栈但不再播自己的转场。`backGestureEnabled` 由 `NativeStage` 在原生层可见时自己决定（不再听网页那份）。
- **弹层**：原生页打开的弹层是原生状态，不进网页 history（网页弹层本来也不跨冷启动恢复，01 §7），所以语义不变。
- **Tab 根**：三个根页与 Tab 栏同一波打开（B3.5d），之前三个根页各自原生但开关默认关，避免一半原生 Tab 栏、一半网页 Tab 栏来回跳。

#### 段 2（B3.F）：真相源翻到原生

当 `listScreens()` 里每个产品屏都有原生类时：

1. 窗口根 = `ShiziRootController`：`UINavigationController`（隐藏系统导航条，页头是 `ShiziPage` 自画）根是 `UITabBarController`（三个根页）。推入页开在 Tab 之上的全局栈（N6），Tab 栏自然只在根页出现。导航代理按目标页的进入方式选 `ShiziTransitions`。
2. **路由提示**：原生持有栈；每次栈或参数变化调 `route.save {stack}`（JS 里仍是 `storage.writeRoute`，单一写入者、免事务写不变），进后台刷新 `at`。
3. **冷启动恢复**：启动时原生调 `route.plan {}` → JS `planColdStart()`（守卫、过期、深链优先、坏值优先、阻断优先全在 JS，不复制）→ 返回要重建的栈与每页视图模型 → 原生无转场重建（S5：时刻不重演）。写字页仍按会话现场恢复（B2）。
4. **深链**：AppDelegate 收到通知 → `deeplink.reminder {cardKey}` → JS `runDeepLink` 的同一逻辑返回「去哪 / 是否要先回首页 / 是否弹 S02」→ 原生 T-quiet 打开。没有 URL scheme，不新增。
5. 网页侧 `app.js` 加「引擎模式」：只建 store、装 API、不挂 UI（`mountRoot` 不调用），网页路由与 root.js 停用；WKWebView 留在窗口里、全尺寸、压在原生根视图下、`isHidden = false`。
6. 量测门槛：冷启动到首页首帧（原生）≤ 现网页版 FCP（160–214ms，01 §4.1），引擎就绪前首页先画「拾」+ 日期的静态版（数据不依赖 store 的部分），就绪后补主按钮文字——**主按钮在就绪前不可点但位置不变**（F4：< 400ms 不显示等待）。

#### 3.4.1 JSC 的时点与做法（若坚持 D69 原文）

- **时点**：B3.F 合并之后、B4.5（SwiftEngine 页面 API）之前，卡 B3.J。前提：B4.6 图片原生已完成（否则引擎里仍要 canvas），或图片继续由一个按需创建、用完销毁的 WKWebView 画。
- **做法**：引入 esbuild（锁版本，devDependency）生成 `Web/engine.js`（IIFE，入口 `src/session/api/index.js` + store boot）；先在 JSContext 里按序执行 `fsrs6.min.js`、`deck-data.js`、`context-overrides.js`、`engine.js`；注入 `callSync / callAsync`（直接调 `NativeStore`）、`setTimeout`、`console`、`performance.now`；`JSCEngine: ShiziEngine` 同步调用；`boundary.test.mjs` 把 `native-boot / native-backend / native-store` 纳入；把 `ui/brand/shi.js` 的四个路径常量挪到 `core/images/`。
- **代价**：约 2 张 Opus 卡 + 新构建工具 + JSC 侧测试；B4.8 后全部删除。**收益**：冷启动少起一个 WebContent 进程（约 50–100MB 内存）、桥调用从 20ms 变 < 1ms——但负责人只测最终态，这些收益只在 B3.F 到 B4.8 之间存在。
- **推荐**：不做，修订 D69（§7 第 1 条）。B4.0 的差分测试不需要 JSC（node ⇄ Swift 命令行，§4.3）。

### 3.5 状态与数据

- 原生页面**不持有业务状态**：每次进入 / `changed` 时拉 `view.*`；页内临时状态（勾选、展开、排序）照网页存在路由 params（`nav.setParams`），冷启动可恢复。

### 3.6 分享图、年报图、月字帖图

- **B3**：图片仍由引擎页面的 canvas 画（`core/images/render.js` 与 `annual-render.js` 不动）。新 op `image.render {job, page?}` → 返回 PNG 的 base64（原生现在只认 PNG，`WebViewController.pngData(fromDataURL:)`），分页时逐页取。图片预览弹层（`image-preview`）原生化：比例分段、「也放进来」、分页翻页、「存好了」、生成中 F4 编排；分享 / 保存直接走原生（不再 postMessage 回来）。

- **B4.6**：`render.js` / `annual-render.js` 用 CoreGraphics + CoreText 重写（同一份 `layout.js` / `paginate.js` / `pick.js` 的 Swift 版给坐标），字体同包内 woff2，纸纹 SVG 两层改为预渲染位图或 CGPath。等价性：node 用网页渲染固定 40 组输入出参考 PNG（Playwright WebKit），Swift 出图逐像素比较——几何（格框、印、墨区掩膜 IoU，与 NP-22 同口径）严格，文字抗锯齿与字距单列容差并具名豁免。

### 4.2 结构

- **`ShiziCore`（Swift Package，只依赖 Foundation）**：config、模型（Codable）、规则、store（对 `KeyValueBackend` 协议编程）、session ops、views。App 引入它；另编一个 macOS 命令行 `shizi-core-cli`（JSON 行协议：`{op, args}` → `{reply, state}`），供 node 差分与调度模拟器用（`ink-model-check.sh` 已有 swiftc 编 macOS 小程序的先例）。
- **`SwiftEngine: ShiziEngine`**：把 `ShiziCore` 的 op 表挂到 B3 的同一个协议上。
- **SQLite**：表结构与键不变（01 §4.1），值仍是同一形状的 JSON 字串；`KeyValueBackend` 的 SQLite 实现直接用 `NativeStore`（同进程、无 XHR）。`store.commit` 语义照搬：按域写时复制 → mutate → 形状校验 → 脏键 → 一个事务 → 成功才发布。

### 4.3 等价性保证（JS 是参考实现）

| 层 | 做法 | 位置 |
|---|---|---|
| ① 金标准向量 | node 脚本用 JS 实现对固定输入生成夹具 JSON（FSRS 每档评分 × 间隔 × fuzz 种子；日期 4 点分界 × 时区 × 夏令时；选字 / 组成；记录折叠；墨 v2 / v3 / v4 编解码；备份解析；schema 校验正反例；图片版式坐标），`--check` 由 node 测试守住与代码同步（`web-ink-golden.mjs` 的模式）；XCTest 逐字段比 | `scripts/core-golden/*.mjs` → `ShiziCoreTests/Fixtures/` |
| ② 现有单测转写 | `test/core`（40 文件 8,151 行）、`test/store`（11 文件 3,317 行）、`test/session` 与 `test/ui/native-*.test.mjs` 的规则部分逐条转 XCTest，用例名保留原名 + 原文件路径注释，便于对账；**转写清单**由 B4.0 生成（每个 `test(...)` 一行，标「转写 / 由差分覆盖 / 仅网页 UI 不转」） | `ShiziCoreTests` |

| ④ 随机化差分 | 种子化随机操作序列生成器（开组 / 写 / 提示 / 看答案 / 判断 / 改判 / 跳过 / 撤销 / 结束 / 换库 / 自选 / 换掉 / 备份导出导入 / 清空 / 撤销 / 时钟前进后退 / 跨 4 点 / 撞配额注入 / 写失败注入），每一步后 JS 与 Swift 的整份状态（规范化 JSON：键排序、数字按 JS 序列化规则）逐字段相等、回包相等；CI 跑 200 个种子 × 300 步，夜间 / 合并前跑 5,000 个种子；失败自动缩小到最短复现序列 | `scripts/core-diff/` |

**数字与 JSON**：JS `JSON.stringify` 的数字格式（整数无小数点、浮点最短往返）与 Swift `JSONEncoder` 不同；比对一律在**解析后的值**上做（浮点按位相等，FSRS 的稳定度 / 难度要求逐位一致——两边都是 IEEE 754 double，同一运算顺序即同一结果；`Math.pow / exp / log` 与 Darwin libm 在个别输入上可能差 1 ulp，FSRS 移植时逐函数核对，差的地方以 JS 结果为准写进金标准并在 Swift 里用同序列算法）。落盘的 JSON 由 Swift 按 JS 同一规则序列化（自写编码器：键顺序按插入序、数字按 ECMAScript Number::toString），使「Swift 写、JS 读」与「JS 写、Swift 读」都逐字节可比（校验和 FNV-1a 也就一致）。

### 4.5 去掉 JS 的时点与回退

1. **B4.8 切换**：`SwiftEngine` 成为缺省；`WebEngine` 仍编进 Release，启动参数 / 隐藏设置可切回（只在 DEBUG 暴露开关；Release 里留代码不留入口，为一版回退）。负责人在这一版统一测试（D67 / 本次授权）。
2. **回退方案**：发现规则差异 → 切回 `WebEngine`（数据兼容见 §4.4），修 Swift、补差分用例，再切。切换不做任何数据迁移，所以切回是零风险操作。

5. **仓库里的 `src/`**：B4.9 后不再进包，但**冻结保留为参考实现与测试先知**（金标准、差分）一个版本周期；网页版（GitHub Pages / PWA）的去留是 D59 ④ 未决事项（§7 第 4 条）。

### 7.2 风险

1. **WebKit 降速**（B2 §10-1）：段 1 与 B3.F 后都必须保证 WKWebView 在窗口里、未隐藏；B3.F 验收量判断往返与视图拉取往返。WebContent 被系统回收时原生页暂不可点、就绪后重拉（§3.4）。
2. **段 1 原生 ↔ 网页混排转场**：一半原生一半网页时，推入 / 返回要截图交接；只存在到 B3.F，按「上面那一层播」一条规则处理，不为单页写特例。
3. **点按到导航的往返**（约 20–40ms）：门槛 p95 ≤ 50ms；超了就让 `nav.push` 回包与视图拉取合并为一次往返。
4. **参考图取证量**（约 110 状态 × 4 组合 ≈ 440 张 + json）：B3.3 时间可能超 L；可拆两半（L0 / L1 页先取，图片 / 备份后取），但都要在对应页面卡前。
5. **夹具数据的可复现**：FSRS fuzz、落款日期、「N 天前」类文案依赖时钟——全部钉时钟，夹具生成器种子化（B2.7 已验证可行）。
6. **B4 浮点与数字格式**（§4.3）：FSRS 计算要逐位一致；`Math.pow` 与 libm 可能差 1 ulp，金标准先跑出差异点再定写法。
7. **B4 一次性切换**：靠影子运行 + 差分兜底，且切回零成本（数据不迁移）。
8. **规则在 B3 / B4 期间还在变**（负责人统一测试前可能有新决定）：B4.0 起任何规则改动都要同时改 JS 与（已移植的）Swift，差分 CI 会拦住只改一边。B4.8 之后规则只改 Swift。
9. **图片像素等价**：CoreText 与 WebKit 的文字光栅化不同，文字区只能容差 + 具名豁免；几何与墨区严格。
10. **体积**：笔顺数据是大头，去掉 JS 只省约 5MiB；真正要省需 B4.10。

**移植时踩到的坑（接着 10.2 / 10.3）**

- **node 的 Math.exp / log ≠ Darwin libm**：V8 用 fdlibm 移植（不是 libm），30 万组里 exp 约 2%、log 约 0.5% 差 1 ulp；而且 darwin-arm64 的 node 是 clang 以 `-ffp-contract=on` 编的，fdlibm 里的乘加被收缩成 FMA——照抄 fdlibm 仍有 0.01% 不同，按 FMA 改写后 120 万组逐位相同（`JSMath.v8Exp / v8Log`）。Math.pow 在 V8 里走 std::pow，与 Darwin 逐位相同。**x86 上的 node 不收缩 FMA，金标准若在 x86 CI 上重生成可能有个别位不同**（夹具在 arm64 Mac 上生成）。
- **设备上的 JavaScriptCore 用 Darwin libm**（本机 jsc 120 万组与 Darwin 逐位相同），所以「现网 JS 的结果」在设备上与 node 并不逐位相同。实测这个差别被 FSRS 的 `toFixed(8)` 吸收：Darwin 口径下 fsrs 金标准 9,318 条全同、模拟器 S3 / S8 / S9（一年长跑）输出逐字节相同。`JSMath.flavor` 缺省 `.v8`（差分的参考），`.darwin` 留给 B4.5 / B4.7 决定（建议 App 内用 `.darwin`，与设备上的 JSC 对齐，影子运行对照的就是它）。
- `+x.toFixed(8)` 要按双精度的**精确二进制值**「四舍五入、同距取大」（`1/512` 正好在中点 → 0.00195313；`1.005.toFixed(2)` 是 1.00）；不能用 `x*1e8` 再 round。
- ts-fsrs 的 fuzz 种子是 `String(review_time ms) + '_' + reps + '_' + String(difficulty*stability)`——要用 JS 的 Number::toString；Mash 逐个 UTF-16 码元、`>>>0` / `|0` 要按 ToUint32 / ToInt32 取模，不能用 Swift 的整数截断。
- `JSON.stringify` 里 undefined 值的键不出现：`{...entry, endedAt: undefined}`、`{fsrs, due: undefined}` 在 Swift 里一律「删键」；`currentCardKey` 在会话写完时返回的是 **null**（不是 undefined），`advance({cardKey: null})` 能通过——随机差分第一轮就抓到这一处。
- `Math.max / min` 有 NaN 就是 NaN、区分 ±0；Swift 的 `max / min` 不是，`jsMax / jsMin` 另写。`Array.prototype.sort` 是稳定的、比较函数 `a - b || …` 的 `||` 把 NaN 当 0；Swift 用自写的稳定归并排序。
- JS 的 Set / Map 按插入序迭代、字符串按码点判等：`KeySet` / `KeyMap`；`practiceStats` 里「这条是不是该字的第一条判断」是按**对象身份**比的，Swift 用下标。
- Date.parse 只实现了 ISO 格式（含 V8 的宽松：日 31 溢出、小写 t / z、空格、小数秒任意位、24:00）；旧式格式返回 NaN（卡与记录里只有 toISOString 写出的串）。`createEmptyCard(0)` 在 JS 里是「现在」，Swift 按 0（时间 0 不会出现）。
- **node 26（V8）的 JSON.parse 有 bug**：夜间差分 Asia/Shanghai 种子 4896 第 195 步，参考引擎把请求里的键 `"\u001f"` 读成了 `"\\"`——前面解析过同形状、键为 `"\\"` 的对象后，隐藏类转移的快路径对转义键判断错了（只用 JSON.parse 就能在同一进程里复现，新进程不复现；Swift 是对的）。参考引擎与比对器改用逐字符解析器 `scripts/core-diff/lib/json-parse.mjs`（语义同 JSON.parse）。别的地方的 JSON.parse 理论上也会中招，但只在这种「转义键 + 前面同形对象」的组合下，产品数据碰不到。
- `node -e` 是 CommonJS 环境，vendor 的 FSRS UMD 会挂到 `exports` 而不是 globalThis——探针脚本一律写 .mjs 文件。

**移植时踩到的坑（接着 B4.1 那一节）**

- V8 的 `Math.hypot` 不是 libm 的 hypot：先按最大值缩放再 Kahan 求和；libm 版在个别输入上差 1 ulp，而 hypot 在弧长、重采样、抽点误差里到处用，字节级比对一定暴露。`Math.exp` 同理（fdlibm + fma 合成，见上）。
- Swift 的 `max(0, .nan)` 返回 0，JS 的 `Math.max(0, NaN)` 是 NaN；`Math.min / max` 对 ±0 有顺序。凡是可能碰到 NaN 的比较都走 `JSMath.max / min`。
- JS 的排序是稳定的、比较函数返回 NaN 当 0；Swift 的 `sort` 不保证稳定：自写归并（`JSX.stableSort`）。
- JS 隐式规则要显式写：真值（空串 / 0 / NaN 为假，数组与对象恒真）、`||` 链（含 NaN）、`Number()`（字符串 / 数组 / null）、字符串 `<` 按码元比、Map / Set 按插入序且覆盖旧键不挪位置、`{...a, k: v}` 已有键保位新键追加、`[...x]` 展开字符串按码点而对象抛 TypeError。
- 正则的细节：`\d` 只认 ASCII；`.` 不含 `\n \r U+2028 U+2029`（`CARD_KEY_RE` 的 `(.+)`）；`\p{Script=Han}` / `Latin` 要查表；`\p{M}` 是 Swift 的 `generalCategory`；`String.contains("")` 在 Swift 里是假。
- 日期 / 时间在边角上要一致：`localDay(NaN)` 抛 TypeError（不是返回「NaN-NaN-NaN」），所以 `fireDayOf` 在时间无效时也是抛；`new Date(y, m, d, h, min)` 的小时分钟是先加到本地时间再换 UTC（夏令时下与「换完再加」不同）。
- Swift 的 `Double → Int` 对 NaN / 超界直接崩：凡是来自数据的数都先判范围（卡片的 `ci`、抽点的上限、重采样段数）。
- 调试构建下 Swift 比 node 慢一个数量级以上（300 字 × 多份编码的容量测试），所以 Package.swift 给 debug 也开 `-O`。
