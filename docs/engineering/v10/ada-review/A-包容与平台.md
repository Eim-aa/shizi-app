# 拾字 · 设计审查 A：包容性与平台契合

审查者视角：包容性（字号、读屏、对比度、减少动态、色觉、单手与触控、尺寸与方向）+ iOS 平台契合（WebView 在哪些地方会被 ADA 评审看出来）。
依据：`.review/corpus/` 截图（iPhone 17 / SE3 / 17 Pro Max，iOS 26.5 模拟器，原生 App）；源码按 `git show 6fb6419`（导出到 scratchpad 阅读）；另在桌面 Chromium 打开 `?test=1` 读了一次写字页的无障碍树（**桌面 Chromium 结果，不是真机 VoiceOver**）。对比度都按 `src/config/tokens.css` 的令牌值用 WCAG 2.x 公式算出，色觉模拟用 Machado 2009 矩阵（重度）。
不重复已修复项（TODO 占位、设置页「跟随手机字号」文案、字库笔迹文案、查字被键盘遮挡、进程被杀不回原页、IME 候选条不出结果）。

---

## 1. 结论

**本视角评分：3 / 10。**（1 = 核心任务对多数辅助技术用户不可用、平台控件全是仿制；3 = Web 语义比一般网页认真，但写字这一核心任务只服务「视力好、手稳、用手指、拿 iPhone」的人，平台行为一眼能看出是网页；5 = 达到 HIG 基本要求的合格 App；7 = 编辑推荐级打磨；8 = ADA 入围；9–10 = 获奖。）
做得好的要先承认：弹层焦点陷阱与焦点归还、页面推入后焦点落到标题、`role=status` 的轻提示、减少动态效果几乎处处有分支、触觉按落定类型分档、深/浅/tinted 三套图标、左缘返回做了跟手与视差。这些让它从 2 分到了 3 分，但和获奖的距离不在这些地方。

**最大的三个差距：**
1. **核心循环只有一条路**：写字只能用手指在 WKWebView 画布上画，没有 iPad、没有 Apple Pencil、没有读屏 / 切换控制 / 语音控制 / 手不稳用户的替代路径；读屏用户连「对照判断」也无从判断（参考字形只读作「参考字形，图像」）。
2. **字号是反的**：完全不响应系统 Dynamic Type（px 写死，AX5 下与默认一模一样，475–478）；App 内唯一的「更大字体」是 1.3 倍开关，而且打开后**书写格从 345pt 缩到 258pt、首页主按钮从 196×190 缩到 141×120**——低视力用户越需要放大，核心区域越小。
3. **到处看得出是网页**：自绘浮动 Tab 栏与页头（无 iOS 26 的玻璃材质与滚动边缘效果，内容直接滚进状态栏下 234）、带把手却不能下拉的弹层、键盘上方 WebKit 的「↑ ↓ ✓」表单附件条（014、471、539）、网页时间选择器的英文「Reset」（055）、全局禁止选字（不能长按查询 / 拷贝一个汉字）、状态栏轻点不回顶、工程只有 `en` 一种本地化（中文系统里的系统界面会是英文，App Store 语言会列为「英语」）、没有小组件 / 快捷指令 / Spotlight。

## 2. 问题清单

严重度：S1 = 拿奖的硬伤；S2 = 明显拉低品质；S3 = 打磨项。

### A01 写字没有任何替代路径（读屏 / 切换控制 / 语音控制 / 运动障碍）— S1
- **页面/状态**：写字页回忆、描一遍、自己写一遍；判断页。
- **证据**：`src/ui/canvas/ink-canvas.js:433-447`，书写格整体是 `role="img" aria-label="书写格"`（`src/config/copy/write.js:78`），画布全部 `aria-hidden`；写字页无障碍树（Chromium 读取）只有「题目 / gān / 书写格（图像）/ 撤销 / 清空 / 看答案 / 提示 / 写好了 / 跳过」。写了几笔不会被读出来，只存在 `data-stroke-count` 里。整个产品没有「在纸上写、回来自判」或「按部件回忆」这类不依赖画布的模式。
- **问题**：VoiceOver 下书写格就是一张图。理论上可以用「轻点两下并按住再拖」的直通手势一笔一笔画，但没有任何读屏反馈（第几笔、写到哪里），也没有方向参照；切换控制和语音控制根本画不了。手抖、帕金森、关节炎的用户在 345pt（大字下 258pt）的格子里用手指写复杂字，没有放宽容错、没有更大的格子、没有别的输入方式。
- **为何重要**：ADA Inclusivity 看的是「不同能力的人能不能完成核心任务」，不看有没有 aria 属性。这个产品的核心任务是「凭记忆把字写出来，再自己判断」，而这里自判是用户自己做的，本来就不需要机器认出笔迹，**替代路径成本其实很低**——这正是能拿来做亮点的地方，现在却是空白。HIG《Accessibility》要求「为依赖辅助技术的人提供同等体验」。
- **获奖级别的目标做法**：
  1. 加一种「在纸上写」模式（设置里或写字页底栏一键切换）：题面照常给，用户在真纸上写，点「写好了」后直接进对照，自判写对 / 写错，记录照常算。它同时服务读屏用户的明眼家人、运动障碍用户和真正用毛笔、钢笔的书法爱好者。记录里标注「纸上」，不存笔迹。
  2. 原生书写面设置 `UIAccessibilityTraits.allowsDirectInteraction`，每落一笔读一次「第 3 笔」，双指轻点读出目前笔画数。
  3. 读屏版「对照」：参考字形的读屏名称包含字、拼音、结构和部件（如「嚏，tì，左右结构，口字旁加疐」），你的书写读出笔画数。用户可以按部件逐个核对后再自判。
  4. 语音控制给「写好了 / 写对了 / 写错了 / 提示」配上可以直接说出来的名称（现在按钮文字可用，要真机确认）。
- **改动范围**：架构（新增模式与记录来源）+ 组件。

### A02 判断页对读屏用户没有信息量 — S1
- **页面/状态**：判断页 167/168；结果页格子弹层 203/283。
- **证据**：`src/ui/screens/write/compare.js:413-422`，两张卡的读屏名称只有「你的书写」「参考字形」（`src/config/copy/judge.js:12-13`）。
- **问题**：读屏用户点到参考字形，只听到「参考字形，图像」，不知道是哪个字，更不知道怎么写，「写对了 / 写错了」这一决定无从做起。产品的立身之本是「本人判断」（D03），对这类用户却等于随机点。
- **为何重要**：Inclusivity；HIG「为图像提供有意义的替代文字」。
- **获奖级别的目标做法**：参考字形的读屏名称写成「嚏，tì，17 画，左右结构：口 + 疐」，可展开逐笔（「第 1 笔 竖，第 2 笔 横折……」，笔顺数据 `strokes.js` 已有）；你的书写读出「你写了 5 笔」。配合 A01 的部件核对。
- **改动范围**：文案 + 组件（数据已有）。

### A03 不响应系统 Dynamic Type — S1
- **页面/状态**：全 App。
- **证据**：475–478（系统字号 accessibility-XXXL / AX5，App 内大字关闭：首页与默认像素级一致）；`src/config/base.css:58` 正文 `font-size: calc(15px * var(--k))`，全局 251 处 `font-size` 里 211 处是「px × --k」、40 处写死 px（如 `src/ui/screens/home/index.js:78-110` 首页日期 / 按钮文字固定 15px，`src/ui/screens/library/list.js:108` 9px）；`--k` 只有 1 和 1.3 两档（`tokens.css` `:root[data-large]`）。iOS 的「单个 App 文字大小」（控制中心）同样无效。
- **问题**：系统层的字号设置是低视力和中老年用户最常用、也最先用的辅助功能。App 只给 1.3 倍上限，而 iOS 正文在 AX5 下约为默认的 3 倍（17pt → 约 53pt）。目标用户是「提笔忘字的成年人」，中老年比例不低。
- **为何重要**：HIG《Typography》「支持 Dynamic Type」；ADA Inclusivity 的评审几乎必查。
- **获奖级别的目标做法**：系统字号是唯一的字号来源，App 内开关改成「在系统字号基础上再加一档」或直接删除。原生实现用 `UIFontMetrics` / SwiftUI 的 `.font(.body)`；如果暂时留在网页里，至少由原生读 `preferredContentSizeCategory`，把连续的倍率注入 `--k`，并在 `UIContentSizeCategory.didChangeNotification` 时更新，同时给 AX1–AX5 单独做版式（底栏纵向堆叠、结果格两列等）。楷体题面和书写格按另一条规则放大（见 A04）。
- **改动范围**：架构（字号模型）+ 样式全量。

### A04 「更大字体」反而缩小书写格和主按钮 — S1
- **页面/状态**：写字页紧凑版 439/433/553；首页 431 对比 357。
- **证据**：`src/ui/screens/write/compact.js:24` `COMPACT_GRID = 258`，标准版是 `ink-canvas.js:31` `STD_SIZE = 345`；`src/ui/screens/home/index.js:123` 紧凑版「拾」按钮 `141×120`（标准版 196×190，`:97`）。439 里书写格明显小于 065；首页今天一行字从 5 个减到 4 个（431）。另外 `policy.compactMaxHeight = 760`（`src/config/policy.js:143`），SE3 等短屏即使不开大字也一直是 258pt 的格子。
- **问题**：低视力用户打开大字，是为了看得清、写得准，结果最需要的东西（写字区域、主操作）变小了，换来的只是周围的说明文字大了 13%–30%。撤销 / 清空还从格子下方挪到了格子上方（065 对比 439），开关一下肌肉记忆就失效。
- **为何重要**：Inclusivity；HIG「放大文字时优先保证主要内容」。这一条评审几分钟就能发现。
- **获奖级别的目标做法**：书写格的尺寸只跟屏幕走，不跟字号走——永远取「屏宽 − 2×边距」与「屏高减去页头和底栏」中较小的那个，Pro Max 上可以到 400pt；大字号下改为让说明文字折叠到「ⓘ」按钮后面、底栏两行改成可横向滚动的按钮组、标题折行，而不是缩格子。首页主按钮在大字下保持尺寸，标题和题记让位。
- **改动范围**：样式 + 组件布局规则。

### A05 不支持 iPad 和 Apple Pencil — S1
- **页面/状态**：全 App。
- **证据**：`project.pbxproj:328/349` `TARGETED_DEVICE_FAMILY = 1`；`Info.plist` 只有 `UIInterfaceOrientationPortrait`；`ink-canvas.js:11` 只有在 `pointerType==='pen'` 时才取压力，但 iPhone 上根本没有笔。没有 PencilKit，没有 Pencil 悬停 / 双击 / 挤压，也没有 Scribble 的考虑。
- **问题**：一个手写类 App，最自然的硬件（iPad + Pencil：真实压力、倾角、240Hz、约 9ms 的系统预测）被排除在外。iPad 上只能以放大的 iPhone 兼容模式运行；横屏、分屏、台前调度都不行。
- **为何重要**：ADA Innovation / Interaction；Apple 历来在评审和推荐中偏爱「把硬件能力用到位」的作品。对这个品类，Pencil 体验就是门面。
- **获奖级别的目标做法**：iPad 原生布局（左侧题面 + 字库侧栏，右侧大书写格；横竖屏都可用）；Pencil 书写用原生触摸管线（`coalescedTouches` + `predictedTouches`，压力与倾角喂给现有的笔锋模型 D09/D10）；双击 Pencil = 撤销一笔，挤压（Pencil Pro）= 弹出「提示 / 看答案」菜单；悬停时在格子里预显落点。手指与笔分开处理（笔写字、手指平移不出墨）。
- **改动范围**：架构（原生书写面）+ 布局。

### A06 导航外壳是仿制的，iOS 26 下一眼能看出来 — S1
- **页面/状态**：所有 Tab 页与子页。
- **证据**：自绘浮动 Tab 栏（`src/ui/components/Tabs.js:12-16`，纯色 `--c` 底 + 0.5px 边，没有玻璃材质，001/230/315）；页面标题是普通 `<h1>`，滚动时不会收成导航栏，内容直接滚进状态栏和灵动岛底下（234：「另有 3 个自选的字」压在 09:41 下面）；`WebViewController.swift:105-107` `bounces=false`、`contentInsetAdjustmentBehavior=.never`，内部滚动由 `overflow:auto` 的 div 负责（`Page.js:26`、`root.js:62`）——所以**轻点状态栏不会回到顶部**，回弹手感来自 WebKit 的 overflow，而不是 UIScrollView。
- **问题**：iOS 26 的 Tab 栏、导航栏、滚动边缘效果都是系统级的视觉语言。仿制版缺材质、缺大标题收合、缺滚动边缘，在玻璃风格的系统里会显得「平」而「旧」。状态栏重叠是明显的视觉缺陷。
- **为何重要**：ADA Visuals and Graphics / Interaction；HIG《Tab bars》《Navigation bars》《Scroll views》。
- **获奖级别的目标做法**：原生 `TabView` + `NavigationStack`（大标题、滚动收合、系统滚动边缘效果），在系统材质之上保留纸色与墨色；状态栏轻点回顶；整个外壳原生，纸张质感留给内容区。
- **改动范围**：架构。

### A07 弹层有把手却拖不动；键盘上方是 WebKit 的表单附件条 — S2
- **页面/状态**：查字 / 自选、外观、结果格对照、清单等所有底部弹层；查字输入时。
- **证据**：`src/ui/components/Sheet.js:18` 画了 36×5 的把手，但整个组件没有任何指针 / 拖动处理（只有点遮罩、返回、Esc 能关）；014、423、471、539、571 键盘上方的「∧ ∨ ✓」是 WKWebView 的 `inputAccessoryView`；539（SE3）弹层底边和附件条之间露出背后的字库页。
- **问题**：把手是系统规定的「可以下拉」的信号，拖不动就是错误的提示。附件条是网页表单的标志，原生 App 不会出现；它还多占了 44pt 高度，在 SE3 上把弹层挤得只剩一行。
- **为何重要**：HIG《Sheets》（把手意味着可调整 / 可下拉关闭）；Interaction。
- **获奖级别的目标做法**：原生 `UISheetPresentationController`（`.medium/.large` 两档，可下拉关闭，键盘弹起时自动升到 large）；查字用原生 `UISearchTextField`，不出现附件条。如果暂时留在网页里：去掉把手，或者把下拉关闭做成跟手；附件条可以在原生壳里隐藏（需评估私有 API 风险）。
- **改动范围**：组件（留网页时）/ 架构（原生化时）。

### A08 工程只有英语本地化，系统界面与 App Store 语言会是英文 — S2
- **页面/状态**：分享面板、存到文件、文件选择、时间选择器、相册权限、文本菜单；App Store 页面「语言」一栏。
- **证据**：`project.pbxproj:130-135` `developmentRegion = en; knownRegions = (en, Base)`；没有任何 `.lproj` / `.xcstrings`；`Info.plist` 没有 `CFBundleLocalizations`。055 里时间选择器的「Reset」是英文（corpus 说明模拟器系统语言是英文，**中文系统下的表现需要真机确认**，但依据本地化规则，App 包里没有 zh-Hans 时，UIKit 会按 en 显示系统控件）。
- **问题**：一个只有中文的 App，App Store 语言写「英语」，分享面板和文件选择器显示「Copy / Save to Files」，会让人质疑做工。
- **为何重要**：Visuals / 打磨；HIG《Localization》。
- **获奖级别的目标做法**：开发区域改为 zh-Hans，加 `zh-Hans.lproj/InfoPlist.strings`（权限说明、显示名），`CFBundleLocalizations = [zh-Hans]`；以后用 String Catalog 管理原生文案。
- **改动范围**：工程配置（半天的工作量）。

### A09 不能选字、不能长按、没有系统「查询」 — S2
- **页面/状态**：全 App，尤其是字库墙、单字详情、题面、结果页。
- **证据**：`src/config/base.css:62-64` 给 `body` 设了 `user-select:none` 和 `-webkit-touch-callout:none`；墙上的格子是普通 `<button>`，没有上下文菜单。
- **问题**：一个关于汉字的 App，用户无法长按一个字拷贝、分享，也调不出系统词典「查询」（iOS 自带《现代汉语规范词典》等中文词典）；墙上的字不能长按预览详情。这些在原生 App 里几乎是白送的。
- **为何重要**：HIG《Context menus》《Text》；Delight（查词就是这个品类的期望）。
- **获奖级别的目标做法**：墙格、详情大字、题面已揭晓的字支持 `contextMenu`：预览单字详情、拷贝、查询（`UIReferenceLibraryViewController`）、加入 / 移出自选、练这个字；详情页的词语、释义允许选中文字。回忆阶段的题面仍然禁止选择，以免泄露答案。
- **改动范围**：组件（网页里可以部分做到，原生才能做全）。

### A10 对比度：按钮和卡片的边界几乎看不见 — S2
- **页面/状态**：判断页「写错了 / 写对了」、写字页「提示 · 还有 N 次」、看答案「自己写」、首页卡片、字库卡片、输入框。
- **证据**（`tokens.css` 计算）：浮纸 `--c` 对纸色 `--p` 浅色 **1.07:1**、深色 **1.13:1**；细边框 `--i5` 对 `--p` 浅色 **1.25:1** / 对 `--c` **1.34:1**，深色 1.48 / 1.30；输入框 `--off` 对 `--p` 1.07（浅）/ 1.27（深）。截图 167、168、063。
- **问题**：次级按钮是「浮纸色块 + 几乎看不见的边」，对低视力或高亮环境下的用户，「写错了 / 写对了」看起来只是两行字，分不出可点范围。WCAG 1.4.11 要求界面控件的边界达到 3:1（文字本身能标识控件时可豁免，但 iOS 的「按钮形状」「增强对比度」开关也都不起作用，见 A11）。
- **获奖级别的目标做法**：次级按钮的描边至少 3:1（浅色约 `#A79F92`，深色约 `#6E665B`），或者改成有明确色块的填充按钮；判断页两个按钮做成更大、更像「印章」的有形控件（同等醒目，D20）。
- **改动范围**：样式 / 令牌。

### A11 忽略系统的「增强对比度 / 粗体文本 / 按钮形状 / 降低透明度 / 智能反转」— S2
- **证据**：源码里没有 `prefers-contrast`、`inverted-colors`、`prefers-reduced-transparency`；原生壳没有读取 `UIAccessibility.isBoldTextEnabled / buttonShapesEnabled / isDarkerSystemColorsEnabled`，也没有把它们传给网页。
- **问题**：原生 App 用系统控件时这些设置会自动生效；这里全部失效。粗体文本对中文细笔画字体尤其重要（PingFang 常规体在低视力下偏细）。
- **获奖级别的目标做法**：令牌层增加一套「高对比」值（主墨、次文字、边框、提示墨、描红轮廓各加深一档）；粗体文本时界面黑体用 Medium / Semibold；按钮形状时次级文字按钮（看答案 / 跳过 / 下一个）加底色；智能反转时，书写格和字形图片标记为不反转（`accessibilityIgnoresInvertColors`）。
- **改动范围**：样式 + 原生桥（或者原生化以后自然获得）。

### A12 字库墙用「墨色深浅」编码时间，最淡一档只有 2.2:1 — S2
- **页面/状态**：字库首页 230/231/234、卡片预览。
- **证据**：`src/ui/screens/library/wall.js:28` 四档不透明度 `[1, .78, .58, .4]`。按主墨叠在纸色上计算：浅色 11.4 / 5.95 / **3.41** / **2.20**；深色最淡档提亮到 .5 后是 3.72。图例只有四条深浅不同的短横（230 底部）。
- **问题**：「多久没写」只靠明度一个维度表达，相邻两档（.78 与 .58）在小屏、户外、低视力和白内障用户眼中几乎分不出来；最淡一档的字达不到大字号 3:1 的标准，「三个月以上没写」的字恰恰是最需要被看见的。读屏名称里写了档位（`wall.js:70-76` `cellLabel`），这一点做得好。
- **获奖级别的目标做法**：明度保留为氛围，同时加一个不依赖颜色的通道：例如按档分组排列（本周 / 本月 / 三个月 / 更早，组间有细标题），或者最旧一档的字下面加一条细的「尘线」；最淡一档不低于 3:1（浅色不透明度约 ≥ .55）。
- **改动范围**：样式 + 组件。

### A13 提示墨和自己的笔迹只靠色相区分；描红轮廓偏淡 — S2
- **页面/状态**：提示 065/066/439/440；描一遍 122/123/519。
- **证据**：提示时本人笔迹降到 35%（`--i1` @ .35）。浅色：提示红 `#A6533F` 对淡化笔迹 **2.54:1**；深色：`#D47A5D` 对淡化笔迹 **1.92:1**。模拟红色盲（protan）后深色只有 **1.67:1**，绿色盲（deutan）2.07:1。描红轮廓 `--tl` 对填充 `--tf` 浅色 **2.65:1**、深色 **2.81:1**，填充对格子底 1.17 / 1.15。说明文字写的是「浅红色是提示」「浅色是参考字形」（`src/config/copy/write.js:24/37`）。tokens.css 头注释也承认「深色下提示笔画、描一遍轮廓待提亮」（W23）。
- **问题**：大约 8% 的男性（红绿色觉异常）在深色模式下，很难把「提示笔画」和「自己写的、淡化了的笔画」分开——现在主要靠提示笔画更细这一点区分。文案用颜色来指认，对他们无效（WCAG 1.4.1 / 1.3.3）。描一遍的轮廓对低视力用户偏淡，看不清要描哪里。
- **获奖级别的目标做法**：提示笔画加第二通道——虚线或带方向的箭头（同时教笔顺），或者在起笔处标笔序号；淡化后的本人笔迹改成更灰、更冷的色调，与暖红拉开明度差（≥ 3:1）；说明文字改成「细线是提示」「描着浅色字写」。描红轮廓至少 3:1，并提供一个「描红更清楚」的开关（增强对比度开启时自动打开）。
- **改动范围**：令牌 + 文案 + 绘制组件。

### A14 题面空格没有读屏名称；拼音读法未验证 — S2
- **页面/状态**：写字页题面 063 等。
- **证据**：Chromium 无障碍树：`group "题目" → "gān"`，紧接着是「尬」；空格这一格只有拼音文本，十字线 `aria-hidden`（`src/ui/screens/write/prompt.js:100-113`，只有重复目标字才有 `role=img` 名称）。
- **问题**：读屏用户听到「题目，gān，尬」，不知道哪一格是要写的、目标字在词的第几个位置。中文 VoiceOver 读带声调的拼音，可能逐个字母读，也可能读成英文（需要真机确认）。
- **获奖级别的目标做法**：空格读作「第 1 个字，要写的字，读音 gān，一声」，整组读作「词语：□尬，写第一个字」。拼音另加 `aria-label`，用汉语的说法读出声调，不依赖 TTS 去猜。可选：轻点题面播放词语的发音（`AVSpeechSynthesizer`，只读词语，不单独读目标字，避免泄露字形，同音字本来就多）。
- **改动范围**：文案 + 组件。

### A15 跳过后的撤销只有 3 秒 — S2
- **页面/状态**：跳过撤销条 189/525。
- **证据**：`src/ui/screens/write/skip.js:36` `SKIP_UNDO_MS = 3000`。
- **问题**：读屏用户要先等撤销条被播报，再把焦点移过去、轻点两下，3 秒通常不够；切换控制、语音控制以及反应慢的老年用户也一样（WCAG 2.2.1「时间可调」）。
- **获奖级别的目标做法**：VoiceOver / 切换控制运行时（原生 `UIAccessibility.isVoiceOverRunning`）撤销条不自动消失，直到下一次操作才收起；普通情况延长到 5–6 秒，手指按在撤销条上时暂停计时；也可以把撤销做成系统 `UndoManager`（三指左滑 / 摇一摇撤销）。
- **改动范围**：组件 + 原生桥。

### A16 书写延迟与刷新率没有用原生能力 — S2（真机证实偏高时升为 S1）
- **页面/状态**：写字页。
- **证据**：`ink-canvas.js:12-13`：WebKit 指针事件 + 有 `getCoalescedEvents` 时才用，**没有预测点**（`getPredictedEvents` 在 WebKit 里不可用）；`policy.js:121` 自己写着「Pencil / ProMotion 真机看过再定」。WKWebView 的 rAF 默认可能锁在 60Hz（iPhone 17 是 ProMotion 屏），需要真机确认。
- **问题**：「笔跟手」是手写类 App 最被评审在意的手感。原生的 `predictedTouches` + Metal / PencilKit 能把可感知延迟压到个位数毫秒，网页画布通常明显落后，并且会因 JS 主线程的工作（保存、Preact 渲染）出现抖动。
- **获奖级别的目标做法**：原生书写面（UIKit + Metal 或 Core Graphics 分层），用合并点和预测点，以 120Hz 渲染；笔锋模型（D09/D10）移植成 Swift。
- **改动范围**：架构。

### A17 没有小组件、App Intents、Spotlight、主屏快捷操作；通知只是文字 — S2
- **证据**：iOS 工程里只有 `AppDelegate / WebViewController / LocalWebSchemeHandler / NativeSmoke`，没有 Widget Extension、`AppIntent`、`NSUserActivity`、`UIApplicationShortcutItems`；提醒通知有词语和拼音（设计不错），但没有操作按钮（`WebViewController.swift:835-900`）。

- **获奖级别的目标做法**：
  - 锁屏 / 主屏小组件：今天的一道题（词语 + 拼音 + 空格），轻点进入这一字的写字页；StandBy 下显示大字题面。

  - App Intents：「拾字，给我出一道题」（Siri 读出词语和拼音），「练写错过的字」快捷指令；Spotlight 可以搜到自己字库里的字。
  - 主屏快捷操作：继续写字 / 自己选字 / 查字。
- **改动范围**：原生扩展（与网页无关，可以先做）。

## 3. 获奖级别的目标形态（最关键的 5 个方面）

1. **一个核心循环，四种写法。** 手指（iPhone）、Apple Pencil（iPad，压力 / 倾角 / 双击撤销 / 悬停）、「在纸上写」（不需要画布，直接自判）、读屏 / 部件模式（逐部件核对 + 直通书写 + 每一笔都有播报）。记录模型只多一个「来源」字段，产品原则（本人判断、看过答案照实记录）不变。这是本作品在 Inclusivity 和 Innovation 两个类别同时立住的关键，竞品里少见。
2. **字号只听系统的，书写格只听屏幕的。** Dynamic Type 从 xSmall 到 AX5 全程连续可用，AX 档单独排版；书写格永远是当前屏幕能放下的最大正方形（iPhone 17 约 362pt，Pro Max 约 400pt，iPad 上 600pt 以上）；楷体题面随字号放大，但不挤占书写格。
3. **系统外壳 + 纸墨内容。** 外壳完全用系统组件（TabView、NavigationStack 大标题、Sheet 档位、上下文菜单、DatePicker、iOS 26 的玻璃 Tab 栏与滚动边缘效果），纸纹、楷体、印章只出现在内容层。系统设置（粗体、增强对比度、按钮形状、降低透明度、智能反转、减少动态效果、按 App 设置的文字大小）全部生效。中文本地化完整。
4. **App 外的「一瞥回忆」。** 锁屏 / StandBy 小组件出题，通知带操作，Siri / 快捷指令「给我出一道题」，Spotlight 能搜到自己的字，长按任意一个字可以「查询」。把「提笔忘字」的那一瞬间从 App 里搬到日常生活中，这是最有可能打动 Delight and Fun 评审的地方。
5. **可量化的手感与对比度。** 书写端到端延迟和 120Hz 渲染有真机测量值（与「备忘录」和 PencilKit 对照）；所有文字 ≥ 4.5:1，控件边界、提示墨、描红轮廓、最淡墨色 ≥ 3:1；提示墨与本人笔迹在三种色觉模拟下都 ≥ 3:1，或者另有形状上的区分。

## 4. 技术形态建议（必答）

| 形态 | 对拿奖的影响 | 成本 | 风险 |
|---|---|---|---|
| **网页壳（现状继续打磨）** | 上限约 5/10。Dynamic Type 可以通过桥接补上，对比度也可以修，但书写延迟与 120Hz、Pencil、直通读屏、系统外壳（玻璃 Tab 栏、Sheet、上下文菜单、查询）、滚动物理都无法真正达到原生水平。评审拿到手里滑几下就会看出来。 | 最低 | 低；但等于放弃 Interaction / Innovation 两个类别 |
| **部分原生（外壳 + 书写面原生，其余页面暂留网页）** | 可以到 7 左右。核心循环和第一印象过关；网页页面要靠视觉统一来掩盖，但切换处（原生导航推进网页页面）容易露出接缝。 | 中 | 中：两套 UI 并存，桥接状态同步；数据仍在 WKWebView 的 localStorage 里 |
| **全原生（SwiftUI + UIKit / Metal 书写面）** | 才有 8 以上的可能。所有平台能力自然获得，iPad / Pencil / 小组件 / Intents 共用同一份数据层。 | 最高：现在 `src/ui` 约 1.4 万行 JS 界面要重写；`src/core` + `src/store` 约 6.8k 行逻辑要移植或桥接 | 已冻结的大量交互决定（D01–D25、边改清单）在重写时容易走样；数据迁移（localStorage → SQLite / SwiftData）一旦出错就会丢记录 |

**明确推荐：以全原生为终点，分阶段迁移；第一阶段先把「书写面 + 写字流程」和「导航外壳」原生化，数据与调度逻辑暂时通过 JavaScriptCore 复用现有 JS，最后再移植。**

**应该原生化的模块（按优先级）**
1. 书写面（`ui/canvas/*`、`write/hint-layer.js`、`answer.js` 的逐笔动画、描红）：UIKit 触摸管线 + Metal / Core Graphics，PencilKit 可以作为 iPad 的备选。这是手感、Pencil、无障碍直通的根本。
2. 写字流程页（回忆 / 提示 / 看答案 / 描 / 自己写 / 判断 / 结果）：SwiftUI，带完整的读屏方案（A01/A02/A14）。
3. 导航外壳：TabView、NavigationStack、Sheet、Alert、上下文菜单、DatePicker、设置（Form）。
4. 查字 / 自选：原生 `searchable` + `UITextField`（IME 合成文字由系统处理，F-1 这一类问题会消失）。
5. 字库墙与单字详情：`LazyVGrid`，上下文菜单与「查询」，大量字的滚动性能。
6. App 外功能：小组件、App Intents、通知操作、Spotlight（这些从第一天起就可以和网页并存，先做也行）。
7. iPad 布局。

**可以暂时留在网页里的**
- 关于 / 隐私 / 致谢 / 许可证（纯文本；最终也可以用原生 `Text` 加 Markdown）。
- 年度报告和分享图片的排版渲染（`core/images/*` 的 canvas 排版）：可以先由离屏 WKWebView 生成图片，再交给原生；以后再移植到 `ImageRenderer` / Core Graphics。
- 领域逻辑（`core/fsrs.js`、`sessions.js`、`records.js`、`schema.js`、`store/migrate.js`、`backup.js`、`query.js`）：先用 JavaScriptCore 承载，原生通过一层 Swift 接口调用；以仓库 `test/` 里的现有测试作为契约，再逐个移植成 Swift，用同一批测试样例核对。
- 字形、笔顺数据和字体（`data/*`、ShiziKai、Noto Serif）直接复用，与网页无关。

**迁移顺序**
0. **现在（不改形态，1–2 周）**：A08 本地化、A19 启动色、A04 书写格不随大字缩小、A03 由原生注入连续的 `--k`、A10/A12/A13 令牌修正、A15 撤销时长、A07 去掉假把手。这些不论最后选哪种形态都要做，而且能立刻提升真机测试的质量。
1. **数据层抽离**：把 localStorage 里的 v2 状态迁到原生的 SQLite / SwiftData，由原生持有；网页通过桥接读写（先做双写和校验，K03 这一类「替换后撤销记录数一致」的测试照搬）。
2. **原生写字流程**：从首页「开始写字」起推入原生写字页，结束后回到网页外壳。这一步最值钱，同时补上 Pencil 管线（暂时只在 iPhone 上，iPad 布局留到第 5 步）。
3. **原生外壳**：TabView + NavigationStack，未迁移的页面作为 `WKWebView` 子页嵌入；字库墙与详情、查字页优先迁移。

5. **iPad + Pencil 完整布局**，横屏、分屏、台前调度。
6. 移除 JavaScriptCore，逻辑全部用 Swift 实现。
