# 拾字 · 交互、动效与手感审查（视角 I）

- 基线：提交 6fb6419（源码一律按 `git show 6fb6419:<path>` 读；下文 `file:line` 都是这个提交的行号）。
- 证据：`.review/corpus/` 单帧截图与 `transitions/` 16 组过渡帧（下文只写编号，如 `#167`、`T-judge-wrong-settle f01`）；另把 `src/core/ink-math.js` + `src/config/policy.js` 拷到 scratchpad，用 node 跑了笔迹管线（匀速直线，60/120/240Hz 采样），结论标「〔管线模拟〕」。
- 没有用浏览器试用，也没有用真机。凡是涉及延迟、刷新率、触觉的结论，都写明「需真机」。笔迹是脚本生成的，不是人手写的，模拟器也没有触觉。

---

## 1. 结论

**4 / 10。** 分档：10 = 获奖作品；8 = 入围水准，核心时刻有独到、可感知的手感；6 = App Store 编辑推荐级，打磨完整、处处像原生；4 = 逻辑周全、状态恢复可靠，但体感像「做得很好的网页原型」；2 = 核心流程不顺或常出错。
拾字的流程设计、失败三段式、撤销条、离开再回来能回到原阶段，都做得比多数 App 认真，所以底子在 4 分以上。但交互评奖评的是「手里的感觉」，这一项目前几乎是空白：

1. **笔迹像记号笔，不像在纸上写字。** 一笔从头到尾宽度只在 9.8–12.9 单位之间变化（约 ±13%）〔管线模拟〕；起笔、收笔都是圆头；竖弯钩写不出钩（`#063`）。对一个以「写字」为全部价值的 App，这是第一硬伤。
2. **核心循环里每个关键时刻都是一帧硬切。** 写好了→对照、判断→下一字、最后一字→结果页、确认看答案→答案卡、答案→描一遍，在 33ms 一帧的录屏里全部是一帧切完。全 App 只有 5 个入场动画，没有一个退场动画。触觉和声音按「盖章」设计，画面上却什么也没发生。
3. **跟手性没有证明，而且结构上有天花板。** 1€ 滤波让墨迹落后手指 3–6pt；抬笔那一帧笔尾才突然收尖（中速时宽度从 11.4 骤降到 5.4）；没有预测点；WKWebView 在 ProMotion 屏上很可能只按 60Hz 刷新。用手指写字时，WebView 目前**还不是**主要瓶颈，笔迹模型和编排才是；但要达到获奖级的「纸感」，书写格最终应改成原生绘制（见 §3-A）。

## 2. 问题清单

### I01 笔迹模型是「等宽记号笔」，没有笔锋　S1

- **页面/状态**：写字页回忆 / 描一遍 / 自己写；判断页左卡；结果页格子；所有缩略图。
- **证据**：`#063`（放大后可见：起止都是圆头，竖弯钩末端是平的，没有钩）、`#133`、`#167` 左卡；`src/core/ink-math.js:77-80`（宽度 = BASE × (1.06 − 0.12·min(v,1.5))，即 0.88–1.06 倍）、`:281`（起笔只在前 6 单位从 0.85 升到 1.08，再回到 1）、`:256-285`（收尖只在抬笔后生效，慢收 endMinSlow=0.9，实际不收）；`src/config/policy.js:124-137`；`src/ui/canvas/brush.js:28-46`（每两点之间画一个四边形，再补一个圆）。〔管线模拟〕：60Hz 下匀速 0.1–1.2 单位/ms，行笔宽度范围 9.78–12.95（BASE 11.5）。
- **问题**：
  - 宽度只跟速度挂钩，变化幅度约 1.3 : 1，肉眼看就是一支 3.3% 格宽的记号笔。真实的硬笔楷书里，横、竖、撇、捺之间粗细比至少 1.8 : 1，毛笔可以到 4 : 1 以上。
  - 没有起笔的「顿」、没有方向相关的宽度（横细竖粗）、没有钩和出锋的生成规则。
  - 飞白是在笔画自己的图层上用 `setLineDash` 擦出的规则虚线（`brush.js:141-156`），纹理很机械。
  - 纸张没有纹理参与，墨色是一块平涂的 `--i1`。
- **为何重要**：ADA 的 Visuals and Graphics 和 Interaction 两个类别。这个 App 的核心价值就是「写」：用户在格子里看见的笔迹就是产品本身。拿记号笔写楷书，「找回手写的感觉」这个承诺第一笔就落空了。
- **获奖级做法**：改成「笔锋模型」。用一次填充的变宽外轮廓多边形替代「四边形 + 圆」的拼接（这种轮廓法已有成熟的开源做法）。宽度由三项相乘：速度、方向（笔画方向相对 −45° 的笔杆角，横约 0.7×、竖约 1.15×）、笔画阶段（起笔顿、行笔、收笔）。起笔在前 40ms 内斜切加宽到 1.35×；慢收时顿笔圆收到 1.2× 并略带洇墨；快收时 25–35pt 内出锋，笔尖收到 0.15× 以下；方向急转超过 100° 且转角后速度峰值超过 1.6 倍均速，判定为钩，并生成钩锋。墨色用纸纹做 multiply 遮罩，抬笔后约 200ms 有「湿墨变干」：不透明度从 0.9 到 1，边缘扩散 0.5pt。具体参数见 §3-A。
- **改动范围**：组件（`ink-math.js`、`brush.js` 重写；存储格式 v3 已带 w/t，可以兼容）。

### I02 核心循环每个关键时刻都是一帧硬切，没有编排　S1

- **页面/状态**：写好了→对照、判断→下一字、最后一字→结果页、看答案确认→答案卡、答案卡→描一遍、描→自己写、自己写→下一字。
- **证据**：
  - `T-recall-to-judge-compare`：f00 是 345pt 书写格，f01（33ms）已经是 166pt 左卡，本人笔迹没有任何中间态。参考字在 f04–f06（133–200ms）才淡入（`compare.js:62`：`.26s` 加 `.12s` 延迟）。
  - `T-judge-wrong-settle`：f00 是判断页，f01（33ms）已经是下一字的空格子，之后 12 帧完全静止。
  - `T-last-judgment-to-result-page`：f00→f01 一帧切到结果页（`write/index.js` 里用 `nav.replace('result')`，不带转场）。
  - `T-confirm-answer-to-answer-card`、`T-answer-to-trace-enter`、`T-trace-to-retrace`、`T-next-card-after-retrace`：都是一帧切换。
  - 全仓 `@keyframes` 只有 Confirm、Sheet、Toast、compare、hint 五处入场动画，退场动画为 0。
- **问题**：
  - 用户的注意力在书写格里。格子内容一帧换掉，换字、换阶段都没有可追踪的变化，看起来像表单提交后刷新了页面。
  - 判断落定时，原生端会发 `Impact medium` 加 82Hz 的「盖章」声（`haptics.js:33`、`sound.js:51-54`），画面上却没有任何东西「落下」，三种感官说的不是同一件事。
  - 换字后有 0.3s 不接受落笔（`write/index.js:57`），这段等待对用户是看不见的（见 I08）。
- **为何重要**：Interaction 和 Delight and Fun 两个类别；HIG Motion 要求动效用来表达状态变化与层级关系。这几帧正是这个 App 每天被重复几十次的地方。
- **获奖级做法**：给 5 个时刻各设计一段 ≤750ms、可被下一笔打断的编排，本人笔迹在其中作为共享元素连续存在。详见 §3-B / C / E。
- **改动范围**：组件到架构（写字页内部要有一层阶段转场，不能只靠 router 的页面转场）。

### I03 跟手性：滤波滞后、抬笔「弹变」、无预测、60Hz 风险　S1

- **页面/状态**：所有书写阶段。
- **证据**：
  - `ink-canvas.js:161-172`：每个 rAF 用 `final:false` 把整笔重画一遍。
  - `ink-canvas.js:243-258`：抬笔后用 `final:true` 重新生成，画进固化层。
  - `ink-math.js:227-234`：1€ 滤波，`policy.js:135-137` 设 minCutoff 1Hz、beta 0.02。
  - 〔管线模拟〕实时笔尖落后原始触点：60Hz 下 2.7 / 4.1 / 5.2 / 6.2 单位（速度 0.1 / 0.3 / 0.6 / 1.2 单位/ms）。
  - 〔管线模拟〕笔尾宽度从实时到抬笔：0.3 时 11.78→9.78，0.6 时 11.36→5.38，1.2 时 10.54→1.25。也就是说，出锋只在抬笔那一帧一次性出现。
  - 没有使用 `getPredictedEvents`，也没有自己外推；`ink-canvas.js:12` 注释写明 iOS 18.1 以前的 WebKit 没有 coalesced 事件。
  - 细节（飞白、洇墨）由 `navigator.hardwareConcurrency` 门控（`brush.js:14-18`）。WKWebView 在真机上返回多少尚未验证；如果返回值 ≤2，真机上所有笔锋细节都会被关掉。
- **问题**：
  - 手指写字时，几 pt 的滞后大部分被指腹挡住。但快写时，「墨追手」加上「抬笔一帧突然变尖」，正是「不像纸」的来源：纸上的墨迹从不在笔离开之后才改变形状。
  - iPhone 17 是 120Hz 屏。如果 WKWebView 的 rAF 被限制在 60Hz（需真机），书写会比系统备忘录明显发涩。
- **为何重要**：Interaction 类别；HIG「Apple Pencil and drawing」与 PencilKit 的标杆（Apple 在 WWDC 2019 介绍 PencilKit 时称 Pencil 延迟约 9ms）。手指书写没有公开标杆数字，但用户会拿备忘录手写做对照。
- **获奖级做法**：
  - 实时笔画用「已确定段 + 预测段」两层：预测段按最近 3 个采样外推 8–16ms，下一帧被真实点替换。
  - 1€ 只平滑宽度，位置只做轻度滤波：minCutoff ≥ 3Hz，或者在最后 20ms 把权重让给原始点。
  - 出锋要在实时阶段就开始：减速趋势出现时，预览收尖逐步介入。抬笔时不再一帧跳变，而是用 60–80ms 的 ease-out 补完收尖。
  - 先在真机上测（§4 第 1–3 项）。如果 motion-to-photon 比备忘录慢超过一帧，或者 rAF 只有 60Hz，就把书写格改成原生 overlay（Metal 或 CAShapeLayer；也可以先用 PencilKit 的 `.fountainPen` 墨水验证手感），原始点仍按现有格式交给 JS。详见 §3-A。
- **改动范围**：组件（管线）；可能升级为架构（原生书写层）。

### I04 看答案：每次弹居中确认框，确认后本人笔迹被清空　S2

- **页面/状态**：回忆→看答案。
- **证据**：`#069`（居中确认框加全屏遮罩）、`#098`（答案卡里本人笔迹已经没有了）；`answer.js:6-9`（确认 commit 时「笔画清空」）；`T-confirm-answer-to-answer-card` f00→f01 一帧切换。
- **问题**：
  1. 看答案是一个高频、低风险的求助动作，却每次都要走一次居中确认（HIG Alerts 说常规操作不该用警告框）。
  2. 求助最有价值的一刻是「我写对了左半边，右边忘了」，而确认之后，本人写的部分被直接抹掉，答案字（`#5D5952` 的灰）占满整格，无从对照「差在哪」。
  3. 答案出现没有过渡。
- **为何重要**：Interaction 与 Inclusivity（帮助应当低成本、不羞辱）；HIG Alerts。
- **获奖级做法**：
  - 用「按住 0.5s 看答案」替代确认框：按钮内有环形进度，进度满时发一次 Impact soft，松手前随时可取消。这样既有意图门槛，又不打断。
  - 答案出现在本人笔迹**下面**：本人笔迹保持 100% 浮在上层，参考字用 28% 的朱色或灰色衬在下面，一眼看出缺了哪几笔。随后「描一遍」直接在同一层上进行。
  - 显影：参考字 opacity 0→1、blur 4→0px，320ms ease-out。
- **改动范围**：组件（answer.js 流程、Confirm 去掉）、文案（确认句改为按钮上的说明）。

### I05 描一遍是「在空心字里随便画」：无逐笔引导，笔宽与字形不匹配　S2

- **页面/状态**：描一遍。
- **证据**：`#122`、`#124`（11.5 宽的细线落在约 30 单位宽的楷体笔画轮廓中间）、`T-trace-stroke-animation-midway`（先播一遍笔顺，15 笔约 4.8s，`policy.js:146-148`）；描红是 `--tf` 填充加 `--tl` 深灰外描线（`answer.js:13`），视觉上像填色本。
- **问题**：
  - 落笔不判断是哪一笔，不提示起点和方向，没有完成反馈。
  - 笔宽只有字形笔画的 1/3，描完仍是「细线在粗字里」。
  - 描完不会收拢成一个完整的字。
  - 唯一的反馈是每次落笔一个纸声（`write/index.js:327`）。
- **为何重要**：Interaction 与 Delight。描红是这个领域最成熟的交互：开源的 hanzi-writer 本身就带逐笔测验模式，项目已经引入了这个库（`glyph.js`）却没有用上。
- **获奖级做法**：
  - 逐笔引导：当前笔用轮廓高亮，起点放一个 6pt 墨点，并用方向箭头淡淡示意。
  - 笔宽自动取字形笔画宽度的约 0.85。
  - 落笔沿方向且落在容差内时，该笔轮廓在 120ms 内被「墨」填满，同时发 Selection 触觉。偏离时这一笔 200ms 淡出，不扣分，不出现「错」字。
  - 全部描完，整字墨色加深一次（200ms），发 Impact soft。
  - 先播笔顺的速度加快到总长不超过 1.6s，任何一次落笔都会跳过。
  - 这样做不是给书法评分（D01 / D03 只禁止自动评美观），只判断「这一笔描到了没有」。
- **改动范围**：组件（answer.js 描一遍阶段、glyph.js）。

### I06 提示是骨架折线，位置不跟随用户已写的字　S2

- **页面/状态**：回忆→提示。
- **证据**：`#065`、`#066`（三条 6pt 宽的朱色折线，起笔处是 medians 的折角钩，并且按标准位置画在右上；用户的「尢」写满了左半格，提示和本人笔迹的比例、位置都对不上）；`hint-layer.js:7-10`、`glyph.js`（`MEDIAN_WIDTH_UNITS = 18`）；写下一笔时提示在 260ms 内收起（`hint-layer.js:49-50`）。
- **问题**：
  - 提示画的是笔画中心线，不是字形，用户看到的是一根铁丝而不是「这一笔」。
  - 用户的字普遍比参考字大或偏，提示落在「标准格」里，和已写部分接不上，用户得在脑子里自己做缩放。
  - 一落笔提示就消失，用户刚想照着写就看不到了。
- **为何重要**：Interaction（帮助要接得上用户当前的状态）。
- **获奖级做法**：
  - 用已写笔画与参考字前 k 笔做一次仿射拟合（缩放加平移，不旋转），把提示变换到用户自己的坐标系里。
  - 提示用楷体笔画轮廓，做朱色 35% 填充加 1pt 描边，每笔 220ms 描出，每笔给一次 Selection 触觉。
  - 收起时机改为「用户写完被提示的那一笔」，或者用户的笔迹覆盖提示面积超过 60%。
- **改动范围**：组件（hint-layer.js 加拟合）。拟合失败（笔数不够）时退回标准位置。

### I07 按下没有反馈；防连点静默吞掉点击和落笔　S2

- **页面/状态**：全 App。
- **证据**：
  - 全仓只有两条 `:active` 规则：`home/index.js:101` 和 `compare.js:75`。`Button.js:47-48` 设置了 `-webkit-tap-highlight-color:transparent`。
  - 「写好了」「提示」「看答案」「跳过」、列表行、tab 按下时都没有任何变化。
  - 另外，iOS WebKit 的 `:active` 通常要求元素或祖先有 touchstart 监听，全仓只有书写格 canvas 上有（`ink-canvas.js:288`），所以连上面两条可能在真机上也不生效（需真机）。
  - `Button.js:38-44`：每次状态变化后 0.4s 内的点击被 `preventDefault` 吞掉，没有视觉提示。
  - `ink-canvas.js:221`：换字后 0.3s 内的落笔被静默丢弃。
- **问题**：
  - HIG 要求控件在 touch-down 时就有反馈。现在用户点了「写好了」，直到下一帧硬切之前，手指下没有任何确认。
  - 防连点本身合理，但吞掉的操作完全静默：用户在换字瞬间落下的第一笔会凭空消失，而换字又是硬切（I02），用户很难意识到「刚才那一笔太早了」。
- **为何重要**：HIG Buttons / Feedback；Interaction。
- **获奖级做法**：
  - 所有按钮在 touch-down 时 80ms 内缩到 0.97，背景加深 6%；松手用 160ms 弹回。用 pointerdown 加类名实现，不依赖 `:active`。
  - 把锁定期做成看得见的：新状态的按钮在 0.4s 内从 60% 不透明度淡入。换字的 0.3s 落笔锁定和换字动画重合（§3-C），动画结束就能写；或者干脆接受这一笔并缓存，到动画结束时再画出来。
- **改动范围**：样式与组件（Button、ink-canvas）。

### I08 转场层叠 bug：下层页的页头按钮压在新推入的页面上　S2

- **页面/状态**：任何子页推入或返回（Page 带 lead/trail 的页）。
- **证据**：`T-list-to-write-push` f01–f08（33–267ms）：「快忘了」页的「全选」始终叠在新写字页的「1 / 5」上（f06–f08 可读出「1全选」），左上角两个「‹」重影。
- **根因**：`Page.js:24` 中 `.sz-page__lead,.sz-page__trail{position:relative;z-index:1}`；`.sz-layer`（`root.js:55`）没有 z-index，也没有 isolation。动画期间上层页带 transform，成为 z=auto 的层叠上下文，下层页的 z-index:1 子元素因此画在它上面。首页已经用 `isolation:isolate` 修过同一类问题（`home/index.js:67-76`），其余页面没有覆盖到。`detail/actions.js:54`（z-index 3）、`library/all.js:57`（z-index 2）同样会穿透。
- **为何重要**：Visuals and Graphics。这种重影在评审的第一次点按里就会被看到，是「网页套壳」最明显的破绽。
- **获奖级做法**：`.sz-layer{isolation:isolate}`，一行即可，然后逐个检查 sticky / z-index 元素。
- **改动范围**：样式。

### I09 页面推入/返回的曲线前冲、底层不动，不像 iOS　S2

- **页面/状态**：所有 push / pop（按钮触发）。
- **证据**：`root.js:45-46`：300ms，`cubic-bezier(.2,.7,.2,1)`。按这条曲线算，33ms 走完 39%，67ms 走完 68%，100ms 走完 83%，后面 200ms 几乎不动。`T-back-button-write-to-home` f01（33ms）写字页已经划出约 3/4。按钮触发的推入时底层页不做视差也不压暗（`root.js:207-212` 只在手势时才动 under）；推入和返回用的是同一条 ease-out。
- **问题**：观感是「闪一下就过去了」，而不是「一页纸滑过来」；层级关系也很弱（底层不退、不暗）。
- **为何重要**：HIG Navigation（推入/返回传达层级）；Interaction。
- **获奖级做法**：
  - 用接近 iOS 的临界阻尼弹簧，约 response 0.5 / damping 1.0，等效时长约 450–500ms。CSS 可以用 `linear()` 把弹簧采样成 20–30 个点（Safari 17.2+；部署目标 iOS 15 时退回 `cubic-bezier(.32,.72,0,1)` 420ms）。
  - 推入时底层同步移到 −30% 并压暗 8%，返回时反向。
  - 可以被打断：转场中再点返回，从当前位置反向，而不是排队等待。
- **改动范围**：组件（root.js）。

### I10 写字页整页禁用左缘返回；离开只能点左上角　S2

- **页面/状态**：写字页（回忆 / 判断 / 答案 / 描 / 自己写）。
- **证据**：`write/index.js:11-13`（整页 backGestureEnabled=false）；corpus README 缺口 11（100 多帧边缘拖动毫无反应）；书写格离屏幕左缘约 22pt（`#061`）。
- **问题**：用户最常停留的页面恰恰不能用全系统通用的返回手势。返回键在 6.3 英寸屏的左上角，单手（右手执笔）完全够不到。
- **为何重要**：HIG Gestures（不要禁用系统标准手势，除非确实冲突）；Inclusivity（单手、手小的用户）。
- **获奖级做法**：JS 把书写格的 rect 报给原生，`gestureRecognizerShouldBegin` 只在起点落在格子外（x<16pt，且 y 不在格子垂直范围内，或格子左边距 ≥ 16pt）时放行。正在写字（isDrawing）时仍然拒绝。返回时如果有未判断的笔迹，提示「已保存，下次接着写」（`#085`，现有的 toast 足够）。
- **改动范围**：组件 + 原生（WebViewController 加 rect 判断）。

### I11 边缘返回判定比系统更容易误触，且忽略反向速度　S2

- **页面/状态**：所有可返回的子页。
- **证据**：`router.js:537-557`：`x > w*0.24 || v > 650`。当 x 超过 24% 时不看速度方向；系统大约以 50% 或明显的正向速度为界。
- **问题**：拖到 40% 再快速往回甩、在 30% 处松手，系统会取消，这里却会提交返回。24% 的阈值也让「拖一点看看下面是什么」很容易真的退出。
- **为何重要**：HIG（手势行为要和系统一致）；Interaction。
- **获奖级做法**：`commit = (v > 500) || (x > 0.5w && v > -200)`，再用弹簧把松手速度接进剩余动画（初速度 = v / 剩余距离）。
- **改动范围**：组件（router.js）。

### I12 底部弹层：有把手却不能下拉；关闭没有退场；关闭后底层抖动　S2

- **页面/状态**：查字弹层、结果修改弹层、外观等所有 Sheet。
- **证据**：`Sheet.js:9-21`（只有入场的 `.28s` 动画，没有拖动处理，`sz-sheet__handle` 只是装饰）；`T-query-sheet-close-by-scrim`：f01（33ms）弹层和遮罩还在，f02（67ms）全部消失；f02–f06 底层「字库」标题从 y≈50 漂到 y≈61（键盘收起时视口变化，被看见了）。
- **问题**：把手是在承诺「可以往下拉」，实际拉不动。HIG Sheets 的默认行为就是下滑关闭。0ms 消失对 280ms 出现，节奏不对称。底层的漂移让关闭显得像是出了故障。
- **为何重要**：HIG Sheets；Interaction。
- **获奖级做法**：
  - 弹层跟手下拉：超过 25% 高度或速度大于 800pt/s 时关闭，否则用弹簧回弹。
  - 有键盘时，第一段下拉先收起键盘。
  - 关闭动画 240ms，曲线 `cubic-bezier(.3,0,.8,.15)`，遮罩同步淡出。
  - 底层在弹层打开时锁定视口高度，不随键盘重排。
  - 如果改动成本允许，查字这类带输入的弹层直接用原生 `UISheetPresentationController` 承载一个 WKWebView 片段：键盘避让、下拉、detent 一次全部拿到。
- **改动范围**：组件（Sheet）；原生弹层属于架构选项。

### I13 触觉与声音点位稀疏，并且和画面脱节　S2

- **页面/状态**：全程。
- **证据**：`haptics.js:32-43`（只有 commit 成功才发：判断 stamp、提示 select、看答案 action、跳过撤销 undo、完成 action）；`sound.js:15`（只有判断与「描一遍落笔」两种声音）；`WebViewController.swift:756-772`（UIImpactFeedbackGenerator，经 JS→原生异步桥）；回忆阶段落笔无声，描一遍落笔有纸声（`write/index.js:327`）；撤销 / 清空 / 结果页修改都没有触觉。
- **问题**：
  - 同样是「写字」，回忆时无声、描红时有声，用户会以为描红「更对」。
  - 「盖章」触觉没有对应的画面（I02）。
  - 撤销、清空是「笔迹消失」的时刻，没有任何确认。
  - 没有用 Core Haptics，做不出连续的「纸感」。
- **为何重要**：HIG Playing haptics（触觉要与可见变化同步、语义一致）；Delight and Fun。
- **获奖级做法**（点位与参数见 §3 各节）：
  - 落笔 transient 强度 0.25、sharpness 0.5，可在设置里关闭。
  - 撤销用 Impact light 0.4；清空用 Impact medium，并配墨迹 160ms 淡出。
  - 判断 Impact medium 和「落印」画面同帧。
  - 描一遍每描中一笔一次 Selection。
  - 可选实验：书写中做 Core Haptics 连续纹理（强度 0.12–0.28 随速度变化，sharpness 0.65），模拟纸的阻力。必须真人测试，默认关闭。
  - 声音：回忆与描红一视同仁。要么都静音，要么都用随速度调制的极轻纸声；默认跟随「按键音」开关。
- **改动范围**：组件 + 原生（Core Haptics 播放器，桥接改成「同帧」触发：JS 在动画关键帧的 rAF 里发消息）。

### I14 一组写完没有任何收束　S2

- **页面/状态**：最后一字→结果页。
- **证据**：`T-last-judgment-to-result-page` f00→f01 一帧切；`T-answer-next-to-result-page` 同样如此；`#201`、`#453`：静态表格，标题「这次记录了 3 个字」，下面大片留白。
- **问题**：练字的满足感本该在这一刻「落款」，现在像打开了一张报表。产品禁止打卡奖惩和里程碑（D01、P08），但这并不排斥一个安静的收束动作。
- **为何重要**：Delight and Fun；Social Impact（让成年人愿意明天再来，靠的是「这五个字是我写的」的手感，而不是数字）。
- **获奖级做法**：见 §3-E（墨迹归位成帖、落款，≤1.2s，可点击跳过，不出现任何夸奖词）。
- **改动范围**：组件（result 页入场编排）。

### I15 掌托误触与「先触为主」的风险　S2（需真机）

- **页面/状态**：写字页。
- **证据**：`ink-canvas.js:215`：非 primary 指针被忽略，而 primary 是「第一个接触的指针」；书写格下沿离「写好了 / 跳过」只有约 100–250pt（`#063`）。
- **问题**：右手写格子下半部分时，小鱼际会先碰到屏幕。这时手掌成了 primary，真正写字的手指被当成第二指忽略，结果是「怎么写不上」。手掌落在格子下方的按钮区时，也可能误点「跳过」「写好了」。
- **为何重要**：Inclusivity（老年用户、大手、侧握）；Interaction。
- **获奖级做法**：
  - 不以「第一个」为主，而是选接触面积小、移动更像书写的指针。原生 `UITouch.majorRadius` 可用；WebKit 是否暴露 `width/height` 需验证。
  - 一个接触在 120ms 内静止且面积大，判为手掌。
  - 书写进行中，按钮区暂时提高触发门槛：笔画结束后 250ms 内，按钮需要 touch-down 与 touch-up 都落在按钮内，且按住时间 ≥ 60ms。
- **改动范围**：组件；如果需要接触半径，就要上原生书写层（与 I03 合并考虑）。

### I16 判断页版式：对照卡被压到 190pt，下方 35–40% 留白　S3

- **证据**：`#167`、`#523`、`#451`。
- **问题**：最需要细看的「我的字 vs 参考字」只有书写格一半大，屏幕下方却有约 650pt 空着。两个按钮在屏幕 60% 高度处，单手能够到，但对照区还可以更大。
- **获奖级做法**：对照卡做到 2 × 175pt（标准机），或者做成上下叠放的大卡（本人在上、参考在下，各 300pt）。按钮放在拇指区（距底 120–200pt）。
- **改动范围**：样式。

### I17 撤销 / 清空：笔迹瞬间消失；「撤销」一词两义；小屏位置漂移　S3

- **证据**：

### I18 Toast、撤销条、确认框都只有入场，没有退场　S3

## 3. 获奖级别的目标形态（关键 5 个时刻）

> 所有时长都按 iPhone 17（120Hz）给出，用「需真机调参」标出必须在设备上调的值。动效都要满足三条：随时可以被下一笔或下一次点按打断；「减少动态效果」时一律换成 150ms 交叉淡化，不缩放、不位移；触觉和画面关键帧同帧（JS 在同一个 rAF 里 postMessage）。

### A. 落笔与运笔：让手指在玻璃上写出「楷书的墨」

- **看起来**：
  - 起笔是斜切的顿点：前 40ms 宽度从 0.9× 涨到 1.35×，切角方向取前 6pt 运动方向加 −45° 的笔杆角。
  - 行笔宽度 = 速度因子（0.65–1.15）× 方向因子（横 0.72、竖 1.12，按 |cos| 插值）× 本体宽。本体宽建议从 11.5 提到 13（345 格），细节真机再调。
  - 收笔：抬笔前 30ms 均速低于 0.25 单位/ms 时圆收，宽度到 1.2×，墨晕 +0.6pt；高于 0.9 时出锋，25–35pt 收到 0.12×；中间线性过渡。
  - 钩：转角超过 100° 且转角后 60ms 内速度峰值超过 1.6 倍行笔均速，就把转角后的段落按出锋处理，并在转角外侧补 0.2× 的顿角。
  - 墨色：主色 `--i1`，纸纹 multiply 遮罩带来 3–5% 的明度起伏。抬笔后 200ms 内不透明度 0.9→1、边缘 +0.4pt（湿墨变干）。
- **怎么动**：
  - 墨迹始终追在指尖上：已确定段加 8–16ms 预测段（预测段宽度 ×0.9，下一帧替换）。
  - 收尖在减速时逐步出现；抬笔只补最后 60–80ms 的 ease-out，不再一帧跳变。
- **触觉 / 声音**：落笔 transient 强度 0.25、sharpness 0.5；书写中的连续纹理和纸声都是可选实验，默认关闭（§4 第 5 项）。
- **工程路径**：
  1. 先在现有 Web 管线里改笔锋模型和收尖时机（不涉及架构）。
  2. 同时在真机上测延迟和 rAF 频率（§4 第 1–2 项）。
  3. 如果和备忘录手写的差距超过一帧（120Hz 下约 8ms），就把书写格改成原生 overlay：WKWebView 上方一个与 `.sz-inkgrid` rect 对齐的 UIView，Metal 或 CAShapeLayer 绘制，`UITouch` 用 coalesced 和 predicted 采样，抬笔后把原始点（现有 encodeRawStrokes 格式）发给 JS。JS 侧的判断、存储、缩略图不变。
- **需真机调参**：方向因子、出锋阈值、预测时长、纸纹强度、本体宽。

### B. 「写好了」→ 对照：真相揭晓的那一刻

- **0ms（touch-down）**：按钮缩到 0.97，背景加深。
- **touch-up**：Impact light（强度 0.5）。
- **0–360ms**：书写格作为共享元素，用弹簧（response 0.42、damping 0.88）从 345pt 缩到左卡的位置与尺寸。墨迹按像素缩放，不重新生成，所以没有跳变。格子的十字线在 120ms 内淡出。
- **160–480ms**：右卡位置的参考字显影：opacity 0→1、blur 4→0px、scale 1.02→1，320ms ease-out。不播笔顺，揭晓要快。
- **480ms 起**：「写错了 / 写对了」两键从 60% 淡到 100%（160ms），把 0.4s 防连点变成看得见的「准备好了」。
- **附加**：按住左卡 → 参考字以 30% 朱色叠到本人笔迹上，松手恢复。这只是「叠看」，不评分，也不着色判定，符合 D03。
- **「接着写」返回**：上面的过程原路倒放，280ms。

### C. 判断落定 → 下一个字：盖一下印，翻一页纸

- **0ms touch-down**：按钮缩到 0.96。
- **touch-up**：Impact medium，与「落印」同帧。左卡右下角出现一枚 14pt 的小印：写对是墨色圆点，写错是赭红点，与字库墙上的红点同一语言。印 scale 1.25→1，弹簧 180ms，加 82Hz 的 stamp 声（保持现有）。两种判断的触觉强度相同，不奖不罚。
- **220–560ms**：左卡连同印缩小飞入顶部结果行，变成「「嚏」记为写错 · 修改 ›」前面一个 20pt 的缩略字。右卡和按钮淡出（160ms）。
- **400–700ms**：下一字的题面加空书写格从右侧 +24pt 处淡入并滑入（280ms，`cubic-bezier(.2,.8,.2,1)`），进度「3 / 5」数字做纵向翻转（200ms）。
- **700ms 起**：书写格可以落笔，替代现在看不见的 0.3s 锁定。250ms 之后的任何落笔都会让动画瞬间收尾，接受这一笔。
- **总长**：≤750ms，连续写 5 个字不会觉得拖。

### D. 求助：提示、看答案、描一遍是一条连续的「放手梯子」

- **提示**：
  - 点按后发 Selection 触觉。
  - 本人笔迹在 200ms 内淡到 45%（现在是 35%，太淡，用户会失去已写部分）。
  - 提示笔画先做仿射拟合，放进用户自己的坐标系，再用楷体轮廓、朱色 35% 填充、每笔 220ms 描出，每笔一次 Selection。
  - 用户写完被提示的那一笔时，提示在 260ms 内淡出；如果用户写的是别处，提示保留。
- **看答案**：
  - 「看答案」改为按住 0.5s：按钮内环形进度，满时发 Impact soft；松手前可以取消。替代居中确认框。
  - 本人笔迹不清空，保持 100% 浮在上层；参考字 320ms 显影到下层（28% 灰）。
  - 卡片底部写「记为看过答案」，与现在 D18 的语义一致。
- **描一遍**：
  - 在同一层上进入，不换页、不硬切。先播笔顺，总长 ≤1.6s，落笔即跳过。
  - 逐笔引导：当前笔轮廓高亮、起点墨点、方向箭头。描中后轮廓 120ms 填墨，加 Selection。
  - 描完整字后墨色加深 200ms，加 Impact soft，自动进入「自己写一遍」：参考字 300ms 淡出，空格子留下。

### E. 一组写完：归位成帖，落款

- **最后一次判断落定**：按 C 的前 220ms 走完（落印），然后不进下一字，而是：
  - **0–500ms**：屏幕上方的结果行和书写格淡出。本组 5 个字的缩略墨迹（或标准字的浅色）从屏幕中央依次落进结果表的格子，每个 300ms 弹簧、间隔 60ms。看过答案、跳过的格子用浅参考字，状态照实。
  - **600–800ms**：表头下方的日期以朱印的方式落款：scale 1.15→1，加 Impact soft。不出现「太棒了」之类的夸奖词，只出现「十月三日 · 写了五个字」这样的事实。
  - **800ms 起**：「再写一组 / 回到首页」淡入。任何点按都会让动画瞬间收尾。
- **这一刻的意义**：用户第一次在同一视野里看到「这一组都是我写的字」。这是把「提笔忘字」的焦虑转成「我还写得出」的地方，也是这个 App 在 Social Impact 类别里唯一能讲的故事。

## 4. 证据缺口（只能真机 / 真人验证）

1. **触点到墨迹的延迟（motion-to-photon）**
   - 方法：iPhone 17、SE3、17 Pro Max 各测一次；用 240fps 慢动作从侧上方拍摄，手指匀速画 10cm 直线，逐帧量指尖接触中心到墨迹末端的距离，除以速度得到毫秒。
   - 对照：同一设备上的备忘录手写，以及一个最小的原生 Metal 画板。
   - 目标：与备忘录的差距不超过 1 帧。
2. **WKWebView 的 rAF 与 pointermove 频率**
   - 方法：在真机 Debug 包中打开仓库已有的 `src/ui/dev/pointer-stats.js`，记录 rAF 间隔分布、pointermove 频率、`getCoalescedEvents` 每帧数量。iOS 18.2 前后各测一台。
   - 判据：rAF 中位间隔约 16.7ms，说明被限在 60Hz，那么原生书写层就是必要条件。
3. **`navigator.hardwareConcurrency` / `deviceMemory` 在 WKWebView 的实际返回值**
   - 方法：在页面上打印，或者 Safari Web Inspector 连接真机读取。
   - 判据：如果返回值 ≤2，那么 `brushDetailEnabled` 为 false，真机上没有飞白和洇墨，现在截图里的笔迹（模拟器跑在 Mac 上）就不代表真机。
4. **`:active` 按下态是否生效**
   - 方法：真机上点「写好了」，同时用 Safari Web Inspector 查看元素状态；或者用 240fps 视频看按钮变化。
   - 用途：决定 I07 只需补样式，还是必须改成 pointerdown 加类名。
5. **触觉与纸声的真人测试**
   - 方法：6–8 人（覆盖 25–65 岁，至少 2 人左手、2 人开大字），A/B 比较「无触觉」「落笔 transient」「落笔 + 连续纹理」三档，各写 10 个字。问是否觉得「更像在纸上写」、是否烦躁，并记录写错率与用时。
   - 判据：只有多数人偏好时才默认开启。
6. **掌托误触（I15）**
   - 方法：让被试右手、左手各写一组，屏幕录制加触点可视化（原生 Debug 层画出所有 UITouch 及其 majorRadius），统计「写不上」与误点按钮的次数。
7. **边缘返回跟手延迟（I10、I11）**
   - 方法：240fps 拍摄拖动，对比系统设置 App 的返回手势，量手指与页面边缘的间距。
   - 判据：差超过 1 帧时，改成原生快照驱动的返回动画。
8. **笔锋参数（§3-A）**
   - 方法：请 2–3 位能写规范硬笔楷书的人在真机上调方向因子、出锋阈值、本体宽，以「像钢笔 / 签字笔写的楷书」为准，把定稿值写入 `policy.ink`（P65）。
9. **动画节奏（§3-B / C / E）**
   - 方法：做原型后，让被试连续完成 3 组共 15 个字，记录总用时。
   - 判据：与现版相比，总用时增加不超过 5%，「拖沓」主观评分不升高。不满足就压缩时长，不砍掉编排本身。
