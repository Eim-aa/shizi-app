# P3 · 状态与异常 评审报告

评委 P3；模拟器 Review SE3（66BBBA9C，iPhone SE 3，375×667 pt）；源码 v10/integration HEAD 2db2cd3。截图在 `P3-shots/`。
方法：模拟器上做了「写到一半杀进程再启动」「写字中途改字号 / 切夜间」「判断按钮连点」「走完首练再开 20 字日常组后改每组字数」；其余情境（跨 0 点、改时间 / 时区、存储失败、恢复备份、v1 迁移、通知权限）无法在模拟器里直接造，从源码和调度模拟报告 S12–S16 取证。评审时间恰好跨过 0 点（10-14 → 10-15），首页日期随之更新为「10月15日」，首练组（不过期）照常继续。

## 1. 结论与打分

**打分：6.5 / 10。** 数据层很扎实：写入有事务日志、读回核对、失败回滚，写字现场杀进程后原样恢复，字号和日夜间在写字中途切换笔迹不丢、不重影，连点判断只记一次，几乎每个写入点都有统一的三段式失败块。扣分处不在「会不会丢」，而在「用户不知道发生了什么、也没有手段」：D65 把每组改到 20–30 字之后，三个原来无关紧要的小边角变成了日常问题——日常组没有「结束这组」；改每组字数对开着的组不生效且无任何说明；隔天或过 0 点没写完的组被无声作废。另外墨迹预算没有跟着 20 字一组放大，笔迹会被静默淘汰，用量预警在代码里没有落地；备份只有手动，没有任何「很久没备份」的线索。

计数：高 2 / 中 5 / 低 5；遗漏功能 4 条。

## 2. 发现清单

### P3-01 日常组（A）没有「结束这组」，20–30 字的组一旦开了只能写完或原样挂着　【高】
- 现象：自选组（B）写字页有「结束这组」；今天的练习（A）和首练没有。D65 之后日常组缺省 20 字、最大 30 字。写到 8/20 想停：点「‹」回首页，首页永远是「继续写字」；已写的 8 个字没有结果页、没有作品图、没有「再写一组」，也没法按新的每组字数重开。想看自己写的那一组，只能把剩下 12 个字写完或跳过 12 次。
- 证据：`src/ui/screens/write/end.js:72-73`（`canEndGroup`：`session.kind === 'picked'`）；截图 `P3-shots/P3-09-daily1.png`（日常组 1/20，底栏只有提示 / 看答案 / 写好了，没有「结束这组」）；`docs/qa/调度模拟报告.md` S16「每天写到一半就退出」每天字数 13.7/20。D22 写的是自选组的完整入口，当时日常组只有 5 字，没有为 20–30 字重新评估。
- 违反：原则 1（常用操作一次点到——「今天先写到这儿」在 20 字组里是常用操作）；交互规范里「每一阶段都能退出」的精神。
- 建议：
  - A（推荐）：日常组也出现「结束这组」，位置、确认框、「已写的 m 个已记下」与自选组完全一致，有判断就进结果页（作品图、再写一组都在那里），零判断回首页。复用现有 `useEndGroup`，只放宽 `canEndGroup` 的条件（去掉 `kind === 'picked'`，保留「未写完」）。
  - B：不加按钮，改成点「‹」回首页时对 ≥ 10 字的组弹一次「结束这组 / 继续」。多一次点击，不推荐。
- 原则检查：A 不增加点击（该按钮对自选组已存在），不增加提示，不增加块；只是把现有入口扩到另一种组。

### P3-02 改「每组字数」对已开的组无效，页面上没有任何说明，用户以为没生效　【中】
- 现象：模拟器上日常组 1/20 时到「我的」点 5，字库「今日练习」仍是「还剩 20 个」，首页仍是「继续写字」。想改成 5 的人恰恰是觉得 20 太多的人，也正是这组还在手上的人。除了源码注释，没有任何一处说「从下一组起生效」。
- 证据：截图 `P3-12-lib-after-size5.png`（还剩 20 个）、`P3-13-mine-size.png`（分段已选 5）；`src/ui/screens/mine/group-size.js:3-5`（只在代码注释里写了「已经开着的组不变」）；`src/config/copy/settings.js:25-27`（没有说明文案）。
- 违反：「提示与实际不符」（选中即生效的控件，效果延迟又不说）；原则 2 的反面——这里是**该有**的、用户能据此行动的状态说明。
- 建议：
  - A（推荐）：与 P3-01 配套，用户可以「结束这组」后立即按新字数重开，行为自洽；并在「每组字数」行没有开着的组时不加任何字，有开着的组时在行下副行写一句「下一组起生效」（只在这个条件下出现，不常驻）。
  - B：改字数时若有没写完的日常组，把它按新字数截短（保留已判断的、丢弃未写的字），需要新规则，风险大，不推荐。
- 原则检查：A 的一句话只在「有开着的组」这个会令人误解的时刻出现，符合原则 2；不增加点击。

### P3-03 隔天 / 过 0 点没写完的日常组被无声作废；过 0 点后的跨天用户错题回来率只有 21%　【中】
- 现象：
  1. 日常组跨天（按 0 点）整组作废（已判断的保留，没写的字重新选），首页按钮从「继续写字」悄悄变成「开始写字」，没有一句话。组变成 20–30 字后，「一天内写不完」「晚上开始、过了 0 点才写完」都是常见情形。
  2. 23:58 开始的组，过了 0 点停在写字页仍能继续提交判断，一回首页整组作废（问题清单 #11 原判「低」，D65 之后建议升级）。
  3. 模拟 S15（每天 23:58 开写，写过 0 点）：写错的字隔天回来只有 **21%**（平均隔 1.84 天），同样的用户 S12（改时间）97.1%、S14（换时区）97.2%——D65 #1「写错的字优先回来」在跨 0 点的用户身上基本失效。
- 证据：`src/config/policy.js:154`（`dailyExpiry = 'discard'`）；`src/core/sessions.js:254-272`（`expireDaily`）；`src/ui/screens/home/index.js:172,196-208`（回前台 / 跨天 safeExpire，结果被忽略）；`docs/qa/调度问题清单.md` #11；`docs/qa/调度模拟报告.md` 第 74–77 行汇总表与 S15 一节「隔天就回来 21%」。
- 违反：状态前后不一致（「继续」突然变「开始」）；D65 #1 的目的。
- 建议：
  - A（推荐）：把「一天」的界线从 0 点挪到凌晨（例如 4 点：startedDay 与「今天」都用 `localDay(now − 4h)`），夜里写字不被切；并为 S15 的 21% 查原因（疑为「昨天写错」的日界与记录的 localDay 在跨 0 点那组上错位，`wrongFirst` 的「最近一次练习日」口径）。
  - B：保留 0 点，但作废发生时首页按钮下一行说「昨天那组没写完，已重新选字」，一次性。
- 原则检查：A 不增加任何界面；B 增加一句提示，只在作废发生的那一次出现。
- 注：跨 0 点实测只在首练组上（首练不过期，没有触发作废）；日常组的作废由源码与 S15 取证。

### P3-04 墨迹预算按 5 字一组时代设定，D65 的 20 字一组会让笔迹被静默淘汰，且没有任何预警　【中】（量级为估算，见待证实）
- 现象：每字只保留「第一次」与「最近一次」的笔迹，超过 1.5MiB 预算后继续淘汰（先中间次，再同一字首 / 末条的其他月）；记录折叠月份时被折掉记录的笔迹一并删除。预算是按「300 字只存最近一次 ≈ 1.1MiB」定的。D65 把缺省改到每天 20 字（调度模拟 S3 九十天学到 258 字、S8 一年 973 字），第一次 + 最近一次 = 每字两份时，按文件头给的单条 3.7KB（UTF-16 估算 ≈ 7.4KB）算，约 200 个字的笔迹就会撑满 1.5MiB，也就是缺省设置下大约 10–20 天。之后月字帖、年度报告、作品图、字详情里较早的字会变成「没有笔迹」。
- 证据：`src/store/budget.js:5-30`（保留规则与回收层级）；`src/config/policy.js:31-33`（`inkBudgetBytes = 1.5MiB`、注释以 300 字为据）、`:341-344`（`storageWarnRatio` 预警「在备份页与首页状态句」）；全 `src/ui` 里没有任何读 `usage` / `warnRatio` 的地方（grep 无结果）——预警没有落地；`src/config/copy/detail.js:16,30`（「没有笔迹」「最近一次没有笔迹，再写一次就能做图片」只在事后出现）。
- 违反：数据丢失（用户自己的笔迹，「我的」页字帖是 D57 选定的主视觉）；「提示与实际不符」（备份页的「记录都已备份」不包含这件事）。
- 建议：
  - A（推荐）：按 D65 的新节奏重算预算（并实测 iPhone 真实 localStorage 配额；现假定 5MiB 未测），让缺省 20 字 / 天至少撑满一年的第一次 + 最近一次；同时落实 `storageWarnRatio`：占用 > 80% 时「备份」行的值文字改成「建议备份」（不加红点、不加弹窗）。
  - B：把笔迹移出 localStorage（原生文件），工程量大，只在 A 不够时考虑。
- 原则检查：A 没有新块；「建议备份」只是已有行的值文字，在用户能据此行动（点进去导出）时才出现。

### P3-05 恢复备份确认框写着「建议先导出」，框里却没有导出入口；离开备份页后无法撤销　【中】
- 现象：选了备份文件后的「替换记录？」框，当现有记录比备份新时写「X 到 Y 的记录会丢失，建议先导出。」，但框里只有「取消 / 替换」。想先导出的人要取消、回到页面点导出、再重新选一遍文件。恢复后「离开这一页前可以撤销」，离开备份页后保护副本即被删除，无法再撤销；换错文件（别人的、很旧的）的人只剩「把旧记录再也找不回」。备份文件里没有任何「这是谁 / 哪台手机」的标识，确认框只显示日期和字数。
- 证据：`src/ui/screens/mine/backup.js:196-206`（`RestoreConfirm`，只有取消 / 确认两键）、`:430-437`（进页面时副本无「续」条件即 `dropSafety`）；`src/config/copy/backup.js` 的 `X-BACKUP.lossRange`；`src/core/backup.js:477`。
- 违反：原则 1（该一次点到的动作要绕三步）；「失败时用户不知道怎么办」。
- 建议：
  - A（推荐）：确认框里「会丢失」那一行右侧加一个文字按钮「先导出」（点了走现有导出，导出完回到确认框）。只在出现「会丢失」时才显示（现有逻辑已有该条件）。
  - B：恢复前自动把现有记录导成一份文件放进系统分享面板，打断感强，不推荐。
- 原则检查：A 是一个只在有风险时出现的文字按钮，换掉的是现在的三步绕路，净点击减少。

### P3-06 保存失败的提示与可点的按钮对不上：写字页「请先导出备份，再重开拾字」旁边却是「再试一次 / 先不保存」，且只提示一次　【中】
- 现象：写字中抬笔写现场失败时弹出的说明是「进度没存上。请先导出备份，再重开拾字。」（空间满的版本是「空间满了，没存上。请导出备份并清理。」），下面的按钮却是通用的「先不保存 / 再试一次」，写字页上没有导出入口；「清理」在 App 里没有对应的操作（唯一能「清」的是清空记录）。这条提示每次页面加载最多出现一次，之后同样的写入失败只置 dirty、不再说话。提示（`hint`）写入失败更是完全静默（「写入失败不阻断」，下次写入再带上）。
- 证据：`src/config/copy/write.js:101-103`；`src/ui/screens/write/persist.js:171`（用 `FailBlock` 套 `notice.text`）、`:154-161`（`noticeUsed` 一次性）；`src/ui/screens/write/hint-layer.js:490-522`（「写入失败不阻断」）；对照 `src/ui/components/FailBlock.js` 头部规范 S1「说明里讲什么、按钮就给什么」。
- 违反：规范 S1；「失败时用户不知道怎么办」。
- 建议：
  - A（推荐）：说明句改成与按钮一致的一句（例如「没存上，刚才的笔画还在这页。」+「再试一次 / 先不保存」），把「导出备份」只放在连续失败（≥ 2 次再试仍失败）之后作为第三个文字按钮「导出备份」；删掉「并清理」。
  - B：保持文案，但在失败块里直接放「导出备份」文字按钮。
- 原则检查：A 不增加正常路径的任何东西；失败路径多一个按钮是出路，不是装饰。

### P3-07 「放进图里 / 拿出来」写入失败没有任何提示，状态不变也不说为什么　【低】
- 现象：结果页每行右侧「放进图里」、分享弹层的「也放进来」是一次提交；失败时返回值被丢弃，界面还是原样，用户再点一次也不知道在做什么。
- 证据：`src/ui/screens/result/index.js:743-746`（`toggleEntry` 不看返回）、`src/ui/images-entry.js:186`。其它写入点（判断、跳过、看答案、结束这组、更正、再写一组、字库 / 查字 / 字详情的各个动作、设置、提醒、备份导出 / 恢复 / 清空）都核对过有三段式。`commitSealed`（记落印）同样忽略失败，后果只是重开结果页时再演一次落印，不算问题。
- 建议：失败时就地换成该行的三段式（「没放进去，再试一次 / 先不放」）。与原则 2 不冲突（这是出错提示）。

### P3-08 备份状态句不含笔迹被淘汰的情况；「记录都已备份」在笔迹被淘汰后仍显示　【低】
- 现象：备份页状态句只比较 judged 记录的签名（`recordsSignature`），笔迹被回收（P3-04）后「记录都已备份」仍成立，但用户的手写已经不在备份里了。
- 证据：`src/core/backup.js:95-105`（只喂 `id + 判断`）。
- 建议：随 P3-04 一起：淘汰笔迹时让签名变，「备份」行值回到「建议备份」。

### P3-09 「我的」页同一屏上两个数对不上：已练汉字 3，本月字帖「全部 2 字」　【低】（可能是规则，但页面没说）
- 现象：首练写了 3 个字（尴写对、赢写错、拾写对），「我的」顶部「已练汉字 3 字」，下面「10月字帖 全部 2 字」。写错的字不进字帖（作品图里也默认不放进图）。规则本身说得通，但同一页的两个「字数」没有任何说明，我第一眼以为是漏了一个字。
- 证据：`P3-shots/P3-10-mine-scrolled.png`。
- 建议：字帖标题行的数字保持，但在字帖块下方那行说明（「二〇二六年十月 两字」）已写的是「两字」，不改；或将「全部 N 字」改成「写对 N 字」。写错字另有归处（字库「待复习」），不加块。

### P3-10 时钟往回拨 / 往西飞：「累计练习」会变少，拨快后写的字拨回来之前不再出现　【低】
- 现象：D63 ④ 的概览把「今天以后的练习日」排除在累计与连续之外：往西飞跨日期线（S14）、被网络校时纠正、拨快再拨回，都会让「累计练习 N 天」减少 1–N 天，累计变少违反字面。拨快 40 天写字再拨回（S13），这些字的到期日在「未来」，调度模拟最长逾期 43 天、积压 89，问题清单 #14 没改。#3（时间倒退写坏稳定度）已按 D65 夹取，判断提交失败 1 → 0，这一点已修好。
- 证据：`src/ui/screens/mine/model.js:251-272`；`docs/qa/调度模拟报告.md` S13 / S14；`docs/qa/调度问题清单.md` #14。
- 建议：低优先级。累计练习不扣未来日（只让连续天数不算未来日）；#14 保持现状并在调度规则说明里写明。

### P3-11 换练习范围：没有一处说明「已开的组不变、旧范围到期的字照常复习」　【低】
- 现象：换范围页直接生效、不确认、不提示（I3 P1-19）。换完后今天已开的组还是旧范围的新字，旧范围里到期的字继续来；用户容易以为「换了就只写新范围」。调度模拟 S6 验证了行为本身正确（新字全部来自新范围，旧字复习照旧；切换当天新字 4 个多 1 个，是 D65 配比换算，不算问题）。
- 证据：`src/ui/screens/library/switch.js:10-15`（头注释写明规则）、`src/config/copy/library.js:21-36`（页面上没有对应句子）。
- 建议：换范围页底注（现有「参考《通用规范汉字表》…」那行）上方加一句固定说明「换范围只影响新字，复习照常。」（常驻一行，不是提示条）。
- 同类：新字都写完的空状态（`session/none.js`）写「可以换练习范围，或先复习旧字」并带「待复习 ›」，而此时「待复习」可能是 0；建议待复习为 0 时不显示该链接。

### P3-12 备份恢复失败原因不分：新版本的备份和损坏的备份给同一句　【低】
- 现象：版本号不认识（备份来自更新的 App）、半坏、缺 meta 都归「没能恢复，你的记录还是原来的。」（无重试，因为重试没用）。更新版本的备份应该说「请先更新拾字」。
- 证据：`src/core/schema.js:660`（`reason: 'version'`）、`src/core/backup.js` `failureKind`（`version` → `restoreFailed`）、`src/config/copy/backup.js` R-B06。
- 建议：`version` 单独一句「这份备份来自更新的拾字，请先更新。」

## 3. 遗漏的功能与入口

1. **日常组的「结束这组」**（见 P3-01）。谁：每天写 20–30 字的人；情境：时间不够写到一半；现在：只能回首页、挂着、第二天作废，没有结果页和作品；最小做法：复用自选组的入口与确认框；理由（原则 7）：入口已存在，只放宽一个条件。
2. **恢复前导出现有记录**（见 P3-05）。谁：换了手机、新手机上写过几天又要导旧备份的人；情境：确认框提示「会丢失」；现在：取消 → 导出 → 重选文件三步；最小做法：确认框「会丢失」行内一个文字按钮「先导出」；理由：防止不可撤销的丢失，且比现状点击更少。
3. **久未备份的线索**。谁：所有用户，尤其写了几百字的老用户；情境：「我的」页备份行现在显示「还没有备份」（`P3-shots/P3-11-mine-bottom.png`），备份是唯一的恢复手段，关于页写着「不会自动备份」（`about.js:26`）；现在：没有任何随时间变化的线索，删 App、丢手机、换手机都靠用户自己记得；最小做法：已有记录且 30 天没备份时，备份行的值文字从「上次备份 X」改成「X 天没备份」（不红点、不弹窗、不 badge）；理由：这是数据层唯一的安全网，改动只是一行已有文字的内容。与原则 5（没有红点）不冲突。
4. **笔迹空间用量的线索**（见 P3-04）。最小做法与上一条合并：占用超过阈值时同一个备份行值文字变「建议备份」；理由同上，`storageWarnRatio` 本来就写了要做、尚未落地。
