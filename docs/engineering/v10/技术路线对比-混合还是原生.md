# 拾字技术路线对比：混合结构，还是原生 App

2026-10-21 · 写给产品负责人做决定用

## 一、现在的拾字是什么

拾字是一个装在 iPhone 上的 App（从 Xcode 安装、有图标、离线可用），内部是「混合结构」：

| 层 | 用什么写 | 规模 | 做什么 |
|---|---|---|---|
| 原生外壳 | Swift（苹果原生语言） | 约 4,600 行 | 启动 App、承载网页核心、提醒通知、触觉、声音、左缘返回手势、原生书写面试验版（约 1,900 行，只在开发版里开着） |
| 网页核心 | JavaScript（网页语言），跑在 App 内嵌的浏览器组件 WKWebView 里 | 约 38,000 行：逻辑与数据 11,800 行、界面 24,400 行、平台桥接 1,900 行 | 全部界面、全部逻辑、全部数据存取 |
| 测试 | JavaScript | 152 个单元测试文件、130 组界面测试、调度模拟器（18 个场景、27 条不变量） | |

为什么是这样：项目最早是网页版（GitHub 上 main 分支、GitHub Pages），v10 重做时沿用「网页核心 + 原生外壳」，先把产品做对，再逐步换成原生。

**这件事其实早有决定。** 2026-10-03 的 D26 写的是：「技术形态以全原生为终点，分阶段：阶段 2 数据层迁原生 SQLite → 原生书写面与写字 / 判断 / 结果流程（逻辑先由 JavaScriptCore 承载现有 JS，test/ 为契约）→ 阶段 3 原生外壳与其余页面 → 最后移除 JavaScriptCore。」之后两周我们一直在阶段 1（网页核心）上打磨界面和规则，阶段 2 只做了书写面试验版，没有往前推。这是主控（我）的排期问题：没有在合适的时候提醒你「该进阶段 2 了」，也没有把混合结构带来的限制讲清楚。

## 二、混合结构给我们带来的问题（都已经实际遇到过）

| 问题 | 原生 App 里 |
|---|---|
| 存储只用了内嵌浏览器自带的小格子（假定约 5MB），每天 30 字约 290 天会满 | 存成文件或数据库，和微信一样，没有这个上限 |
| 写字跟手：网页画布有额外延迟，为此做了原生书写面试验版 | 原生触摸 + Metal 直接画，能用 Apple Pencil 压感、预测点 |
| 左缘滑回不灵、整页能被拖动、弹窗关闭卡一下、页面切换要自己模拟 | 系统导航、系统弹层天生就是这样，免费、和其他 App 一致 |
| 动效要自己做一套规范和检查去模仿 iOS | 大部分直接用系统组件，天然符合 |
| 大字号、读屏要手工对齐 | 系统组件自带 Dynamic Type、VoiceOver |
| 每改一处要在模拟器 WebKit 里额外检查一遍（iPhone 内核检查） | 不需要这层 |
| 苹果审核：纯「网页套壳」可能被拒（审核指南 4.2），我们是本地打包、有原生功能，风险不大但存在 | 无此风险 |

混合结构也有好处：一套代码、改起来快、测试工具成熟（Playwright）、已经写了 38,000 行而且测得很细。

## 三、三条路

### A　保持混合，只把存储改成文件

- 做法：笔迹（以后也可以是全部数据）经原生桥存成手机上的文件。
- 时间：约半天到一天（加检查）。
- 解决：存储会满。
- 不解决：手感、手势、弹层、动效这一类问题会继续出现，继续一个个修。
- 适合：近期就要上架、先求稳。

### B　按 D26 逐步原生（推荐）

每一步完成后 App 都是能用、能装、能测的，不会有「几周什么都看不到」的阶段。

| 步 | 内容 | 预计 | 完成后你能感到的变化 |
|---|---|---|---|
| B1 数据层原生 | 记录、调度、笔迹存进原生 SQLite 数据库；网页核心经桥读写；一次性迁移 | 约 1 周 | 存储不再有上限；数据更安全 |
| B2 写字页原生 | 书写面（试验版转正）+ 写字、判断、结果三页用 SwiftUI / UIKit 重写；出题、判断、调度这些规则先由 JavaScriptCore 直接运行现有 JS 代码，单元测试当作「规则合同」保证一模一样 | 约 2–3 周 | 写字跟手、Pencil 压感、核心流程手感变成原生 |
| B3 外壳与其余页面原生 | 首页、字库、我的、字详情、查字、备份、年报等改 SwiftUI；导航、弹层、手势用系统的 | 约 2–3 周 | 全 App 手感和系统 App 一致；左滑、弹层等问题自然消失 |
| B4 逻辑改写成 Swift | 把规则从 JS 移植到 Swift，用同一套测试与调度模拟对齐结果，移除 JavaScriptCore | 约 1–2 周 | 用户感受不到；之后维护只有一种语言 |

- 合计约 6–9 周（按现在多个开发并行的节奏；期间仍能接收你的反馈）。
- 风险：两套代码并存的过渡期，改规则要同时考虑两边；每步都要做数据迁移与对照测试。
- 好处：每一步都能装到手机上试；规则（D01–D66）、调度测试、文案表直接复用；可以随时在某一步停下来上架。

### C　一次性全部用 SwiftUI 重写

- 做法：新建一个纯原生工程，界面和逻辑全部用 Swift 重写，做完再替换。
- 时间：约 5–8 周，中间几周手机上看不到新东西。
- 好处：最干净，没有过渡期的双份代码。
- 风险：最大。38,000 行一次性重写，中途发现问题要等很久才看得到；现有的界面测试（130 组）基本作废，要重新写原生的 UI 测试；B 方案里「每步可装可试」的反馈节奏没有了。

## 四、无论选哪条，都能直接沿用的

- 全部产品决定 D01–D66、交互与动效规范（原生后很多条变成「用系统组件即自动满足」）
- 设计系统：颜色、字号、间距令牌（tokens.json），楷体 / 宋体字体子集
- 文案表（688 条）与说法规范
- 出题与复习规则、调度模拟器、27 条不变量（原生后用它们验证结果一致）
- 笔顺数据、字库数据、易忘度字表
- 原生书写面试验版与笔锋模型规格

## 五、我的建议

选 **B**，并且从 B1 开始：

1. B1 先做，因为它同时解决「存储会满」，而且是后面所有步骤的地基。
2. B2 紧接着做，因为写字是拾字的核心体验，也是苹果设计奖最看重的部分。
3. B3、B4 按你的真机反馈节奏推进；如果中途想先上架，可以停在 B2 或 B3 之后。

如果你更在意尽快上架、手感问题可以先忍，就选 A，之后再按 B 走。

## 六、需要你定的

1. 选 A、B 还是 C。
2. 选 B 的话：是否同意按 B1 → B2 → B3 → B4 的顺序；B 期间网页核心只修 bug、不再加新的界面打磨（避免两边都改）。
